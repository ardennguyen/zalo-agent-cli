## zalo-agent-cli 2.1.0

> Proposed release notes. Publish only after PRs #2, #3 and #4 are merged into
> `v2.0-dev`, the release version/lockfile are prepared, and the integrated
> candidate passes CI. No tag or release has been created.

More accurate sender identities, account-specific daemons, and sync requests
directly from MCP. Requires Node.js 22 or newer (22.19+ in practice).

### Highlights

- **Current names without losing historical names.** Message reads add
  `senderDisplayName` and `senderDisplayNameSource`, resolved by UID with your
  alias first, then Zalo's profile name, then UID. Stored `senderName` remains
  the historical/first-known snapshot. Alias removal and profile renames appear
  on later reads; reading does not rewrite message history.
- **Pin each daemon to an account.** `listen --account <ID>` and
  `mcp start --account <ID>` accept a full registered numeric account ID. Startup,
  reconnects and retries use the selected credentials. Without the flag, the
  active account is captured at startup. The shared active account is unchanged.
- **14 MCP tools instead of 12.** `zalo_sync` requests a message restore or
  reaction-backlog sync; `zalo_sync_status` reads progress and the final result.
  Start returns a job immediately. Message restore still needs a tap on the phone.
- **One socket and one writer.** MCP sync uses the daemon's existing runners and
  stage lock, shared with CLI sync, history and self-heal. Retrying the same
  requestId and arguments returns the retained job instead of another phone prompt.

### Fixes worth knowing

- Phone-restored senders are mapped to real UIDs where profile resolution succeeds;
  replay can fill missing identities without overwriting established names/UIDs,
  recalled messages or attachment state.
- Sync refreshes cached 1-1 conversation names, including peers outside the
  restored message window, without changing conversation activity ordering.
- A reconnect cannot switch a pinned listener/MCP process to a newly active account.

### Compatibility and licensing

- Current-name fields and account flags are additive. No database schema migration.
  Existing rows with unresolved identities need another message restore using this
  engine; a history read alone does not enrich them. Names missing from the original
  transfer can only be filled from the profile seen during restore, not reconstructed
  historically. Back up the account database before an operational restore.
- Since the post-2.0.0 licensing change, source is **CC BY-NC-SA 4.0**. See
  `LICENSE` and `NOTICE` for terms and commercial licensing information.

### Known limits

- Name/profile resolution is best-effort; unresolved identities remain explicit.
- One web session per account still applies. Separate processes need separate IDs.
- Jobs live in RAM: the last ten jobs and twenty recent events per job are kept.
  Restart/eviction loses status and retry deduplication. No cancellation or automatic
  resume is exposed. A completed runner may report partial/timeout/socket-lost;
  inspect its result and `zalo_coverage` before claiming a full restore.
- Media, boards, cloud index and conversation-state sync remain CLI operations.
- New behavior has offline regression coverage, including stdio/HTTP transports.
  Live multi-account reconnect, alias/profile changes and phone sync remain unverified.
- Unofficial API; existing account and one-web-session constraints still apply.

### Upgrade

After this version is published:

```bash
npm install -g @ardennguyen/zalo-agent-cli@2.1.0
```

Wrapper users should wait for `zalo-mcp` 1.1.0 with engine range `^2.0.1`, then
use the wrapper's documented update command. The range alone does not update an
already installed engine. No local deployment is changed by these PRs.
