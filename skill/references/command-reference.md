# zalo-agent CLI — Full Command Reference

Exhaustive reference for every command, subcommand, and flag `zalo-agent` exposes. Generated by reading every file in `src/commands/` and `src/mcp/mcp-tools.js` directly (not from prior docs), current as of v2.2.0.

## Global Behavior

- **`--account <id>`** (global flag, works before or after any command; env: **`ZALO_ACCOUNT`**) — pin this invocation or daemon (`listen`, `mcp start`, or any one-shot CLI command such as `msg send`, `conv recent`, `sync`, `whoami`, `status`, `logout`) to an exact, full numeric registered account ID without changing the shared `active` entry in `accounts.json`. Omitting the flag uses the active account (and for `listen`/`mcp start`, pins that active account at startup across reconnects and retries). Names, partial IDs, and empty values are refused; an unregistered ID fails immediately before authentication. For `listen` and `mcp start`, the selected account's lock is acquired before authentication and a mismatched authenticated UID is rejected. Running multiple live accounts simultaneously is done by running one `listen` or `mcp start` process per `--account <id>` (and passing `--account <id>` on concurrent CLI invocations). See [English](../../docs/account-pinning.md) / [Tiếng Việt](../../docs/account-pinning.vi.md).
- **Current versus historical names:** `msg history`, MCP history and buffered-message reads preserve `senderName` and add `senderDisplayName` plus `senderDisplayNameSource` (`alias`, `zalo`, `uid`). Display uses this account's explicit alias, then the fresh profile's `zaloName`, then UID; it never rewrites the message snapshot. CLI text history prints the current label. Sync refreshes cached DM titles even outside the restored message window without changing activity timestamps. See [English](../../docs/current-user-names.md) / [Tiếng Việt](../../docs/current-user-names.vi.md) for failure behavior and restoration limits.

- **`--json`** (global flag, works before any command) — machine-readable JSON output for every command. Also suppresses the startup disclaimer and the "Note:"/`info()` lines that would otherwise print to stdout.
- **`--env-file <path>`**, **`--config-dir <dir>`**, **`--credentials-dir <dir>`**, **`--data-dir <dir>`**, **`--media-dir <dir>`**, **`--oa-dir <dir>`** (global flags, work before any command) — load a `.env` file (`--env-file` / `ZALO_ENV_FILE`, plus automatic loading of `./.env` and `<CONFIG_DIR>/.env`) and override the default `$HOME`-based storage roots so config (`accounts.json`, `mcp-config.json`), personal session credentials (`cred_<ownId>.json`), per-account database & runtime state (`<ownId>/zalo.db`, `daemon.lock`, `daemon-channel.json`), downloaded media (`<threadId>/`), and Official Account credentials (`oa-credentials.json`) can live on separate volumes or mounts in production. Equivalent to setting `ZALO_CONFIG_DIR`, `ZALO_CREDENTIALS_DIR`, `ZALO_DATA_DIR` (or `ZALO_DB_DIR`), `ZALO_MEDIA_DIR`, and `ZALO_OA_DIR`; CLI flags take precedence over environment variables, which take precedence over `.env` files.
- **`-V, --version`** — print the installed version.
- **`-h, --help`** — help for the CLI or any subcommand (`zalo-agent <group> --help`).
- **Disclaimer**: on every command *except* `oa` commands and JSON mode, the CLI prints: "This tool uses unofficial Zalo APIs (zca-js) — your account may be banned. Use at your own risk." (VN translation included). `oa` commands are exempt because they use the official Zalo OA REST API.
- **Auto-login**: before running any command, the CLI auto-logs-in the target account (`--account <id>` / `ZALO_ACCOUNT` if set, otherwise the active account in `accounts.json`) — *except* for `login`, `account`, `help`, `version`, `update`, `oa`, `listen`, and `mcp` (these manage their own auth or don't need one).
- **Update check**: a non-blocking background check against the npm registry runs before every command except `update` itself. It is silently skipped when stdout is not a TTY (piped/scripted use), in `--json` mode, or when the env var `ZALO_AGENT_NO_UPDATE_CHECK` is set. It only ever warns when a genuinely *newer* semver version is published — a local dev build ahead of npm (e.g. `2.0.0-dev` vs published `1.0.7`) will not trigger a false "update available"/downgrade warning.
- **Thread type flag** (`-t, --type <n>`), used across almost every messaging/thread command: `0` = User/DM (default), `1` = Group.

## Top-Level (Auth & Maintenance)

| Command | Description |
|---------|-------------|
| `login [-p, --proxy <url>] [-n, --name <label>] [--qr-url] [-q, --qr-port <port>] [--credentials <path>] [--sync] [--sync-days <n>]` | Login via QR scan, or from an exported credentials file (`--credentials`, skips QR entirely). **`--sync`** (QR login only) restores the message history right after the login with the key the phone offers when **"auto sync" is ticked** on its QR confirmation screen: no tap is needed, because the phone's `transfer_after_login` control carries a short-lived key that the conversation request sends (what Zalo Web does). `--sync-days <n>` limits it to the last N days. Without a key (not ticked, or older than two minutes) nothing is started and the command says to run `sync`; a daemon holding the account also skips it. The key is read from the control queue the moment the socket is up, so the sync starts within seconds of the scan. A local HTTP server for viewing the QR in a browser always starts (default port 18927, override with `--qr-port`); `--qr-url` is accepted but the server starts regardless — useful to remember for VPS/headless use. During the QR flow the CLI now surfaces every zca-js QR event: generated (shows QR + starts HTTP server), **scanned** (prints who scanned it — name + avatar URL — and prompts to confirm on phone), **declined** (login fails immediately, does not hang until the 60s timeout), and **expired** (auto-retries with a fresh QR, since zca-js itself doesn't). |
| `logout [--purge] [--delete-history] [--no-remote] [--keep-session]` | A real logout on this device: signs the device out at Zalo the way Zalo Web does — six calls (a one-time token from `id.zalo.me`, the profile `deactive` call, the `v2` logout, `id.zalo.me`'s own logout, the `setsid` hops, the login page) — then tries the saved login once, and reports the device as signed out only when Zalo refuses it (a saved login that still works is a warning that points at the phone's list of logged-in devices). It then **deletes the saved credentials**, so the next command needs a new QR login. The chat cache is kept for that next login. `--keep-session` does only what `logout` did before v3.0: it ends this process's session *key* (the production `GET /api/login/logOut`, then `logoutV2()`), which leaves the saved login valid at Zalo and the device in the phone's list until it is removed there; the credentials are still deleted. `--no-remote` skips every server call (the credentials are still deleted). `--delete-history` also deletes the local chat cache (`zalo.db` + downloaded media), matching Zalo Web's "Delete chat history on logout" checkbox. `--purge` fully removes the account from this machine: wipes the *entire* per-account data directory (db, media, sync keys, daemon.lock — same as `account remove`), deletes the saved credentials, and removes the account from the registry. All three refuse to delete anything while a `listen`/`mcp` daemon holds the account's lock, naming its PID — stop it first. Stopping and restarting a daemon is not a logout: the credentials stay, it logs back in, and self-heal catches up what arrived meanwhile. |
| `status` | Show current login state: logged in y/n, own user ID, active account name/proxy. |
| `whoami` | Show current user's full Zalo profile (fetched live) and when the saved session ends (`sessionExpiry` in `--json`). Nothing in Zalo extends the saved login (its session cookie is set once, at login, for about 90 days), so the date is shown before it arrives. |
| `update` | Self-update: runs `npm install -g @ardennguyen/zalo-agent-cli@latest`. |
| `sync [-F, --force] [-d, --days <n>] [--from <date>] [-w, --wait <seconds>] [--no-messages] [--no-reactions] [--no-conv-state] [--no-boards] [--no-cloud] [--no-media] [--no-removals] [--shard-size <n>] [--full-resync] [--plan]` | **One run that pulls every kind of message state** — the command to use by default. Reactions, pinned conversations, notes, polls and reminders are all state of the messages and conversations; they used to need five separate commands, two of which each opened their own socket and took their own lock, so a full refresh evicted Zalo Web twice. `sync` runs them as stages of one process with one lock and one exit code: **(1)** open the WebSocket once, with one live-store tap for the whole window so nothing arriving during the run is lost; **(2)** the message restore (cmd 590/591) — the **only phone prompt, at most once per run** — alone, exactly as `sync-mobile` runs it; **(3)** the reaction backlog drain (cmd 610/611) on the same socket. (A first version drained reactions concurrently with the restore, as Zalo Web does on connect; the restore then lost its socket with close 1006 at batch 0 on both live attempts, while the same 30-day window restored 11,324 messages through `sync-mobile` minutes later.) **(4)** retry reactions whose message was not stored when they arrived; **(5)** close the socket, wait for it to actually close, release the lock; then the REST stages **(6)** pinned and unread conversations into `conv_state`, **(7)** boards (notes, pinned messages, polls, reminders), **(8)** the zCloud index, **(9)** media last. The socket is opened once and never restarted, because zca-js's `stop()` resets the listener and the socket's own onclose resets it again later — a stop-then-restart between stages races and nulls the new socket. **A running `listen`/`mcp` daemon is never evicted, and no longer has to be stopped**: when one is up, the socket stages (2)–(4) run **on that daemon's socket** over the loopback channel it advertises in `daemon-channel.json`, streaming their progress back so the run prints exactly as it would locally, while the daemon keeps capturing live traffic throughout. This process opens no WebSocket and takes no lock; the REST stages run here as always. The old answer — stop the daemon, sync, restart it — opened a fresh coverage gap of its own (~70s between the restore's snapshot and the daemon coming back, unrepairable since `pullMobileMsg` answers empty). The phone tap is unchanged: routing removes the second WebSocket, not the confirmation, and the daemon never starts a sync on its own. A daemon that is up but published no usable channel still causes the socket stages to be skipped with that reason. `--plan` shows the routing in the transport column (`socket→daemon`) and as `viaDaemon` in `--json`. The message restore is debounced exactly as `sync-mobile --transfer` is (`--force` to override); the reaction backlog is not, since it never prompts the phone — `--no-reactions` together with a fresh restore opens no socket at all. `--plan` prints each stage's order, transport, whether it would run and why, and exits without sending anything. Ends with a one-line-per-stage summary (`ok`, `partial`, `skipped`, `unavailable`, `unconfirmed`, `failed`); with `--json` that summary is the single JSON document on stdout. Exits 1 only if a stage failed — an account without zCloud reports the cloud stage `unavailable`, not failed. Stage tuning (`--pages`, `--kind`, `--prune`, …) stays on the per-stage commands below, which remain for re-running a single stage. **Pinned and unread, as measured live:** pinned ids arrive prefixed with the thread kind (`g<groupId>`, `u<userId>`) and are stripped; unread-mark ids arrive as JSON *numbers*, so a 19-digit thread id is rounded before zca-js returns it (`4123456789012345678` → `4123456789012346000`). It is matched to the one cached thread that rounds to the same value, and an ambiguous match is reported, never guessed. **The socket is kept alive and a dropped one is resumed.** Zalo's own WebSocket heartbeat (`cmd 2/1`) runs on the interval the server hands out at login — measured at 180000 ms, which is the entire width of the phone wait — so the run sends the same frame on that interval for the whole socket window, as Zalo Web does, and counts the server's echoes, which is the only trace a bare `1006` (no close frame) leaves. `1006` is **not** in the server's own `close_and_retry_codes`, so zca-js never retries one: if the socket drops mid-restore the run pauses 2 s (Web's shortest retry), reconnects up to **three** times, first releases the dead socket's sessions with reason 3 and counts them again, and re-requests only the batches that never arrived, keeping everything already stored. Sessions are requested up front in waves of up to 30 (the phone stops serving at about 32 open together) and a wave is released one session at a time once it is stored; a session the phone leaves incomplete and idle for a minute fails alone and its conversations are asked for once more at the end. Re-tapping the phone is the expensive part, so this is strictly better than failing — worst case the phone prompts a second time, which is what a manual re-run would have cost anyway, and the run says so explicitly when it happens. A failure now distinguishes **the socket died** from **the phone never answered**: they need opposite things from you. **`--shard-size <n>`** (1–30, default 30) sets how many conversations go in each message batch; fewer means more, smaller batches, so the first one comes back sooner and less is lost to a drop, at the cost of more sync sessions. The server rejects a batch of more than 30. **A run remembers what it settled.** Per conversation, `zalo.db` records the window a restore settled (`sync_ranges`): a killed or partial run is finished by the next one, which asks only for the conversations that did not finish; a conversation that has moved on since is asked for only from where the last run stopped; a conversation the phone could not serve (or whose batch could not be downloaded) is asked for once more in the same run, and stays failed for the next if it fails again. Every request is acknowledged by Zalo (10 s, retried), every session is released with the reason that fits how the run ended, and sessions a dead run left open are released as outdated at the next start. A run that did not settle its whole window records no success, so the "synced recently" shortcut never hides unfinished work, and does not apply while a conversation range is unfinished. **`--full-resync`** forgets all of it and asks for every conversation in full. **Ctrl+C** during the restore stops it cleanly: what already arrived is kept, the sessions open on the phone are released (as cancelled), nothing is recorded as settled, and the result says `cancelled`; a second Ctrl+C quits at once (exit 130). |
| `sync-mobile [--socket] [-F, --force] [-d, --days <n>] [--from <date>] [-M, --messages-only] [-w, --wait <seconds>] [--shard-size <n>] [--full-resync]` | Restore message history from the phone into the local cache (`zalo.db`). **This is the real, phone-backed restore (transfer-sync-v2, socket cmd 590/591), and it is now the default — no flag needed.** `-t/--transfer` is still accepted and ignored, so scripts and older docs that pass it keep working. It sends ONE sync request the owner confirms on their phone (tap "ĐỒNG BỘ NGAY"), enumerates every conversation (conversation round), then requests message history in shards of ≤30 partitions (server cap), decrypts each batch with Zalo's `libzproto` WASM (fetched+cached from Zalo's CDN on first run), Zstd-decompresses, protobuf-decodes, maps each opaque conversation id to the real numeric threadId + name via the friend/group lists (both expose `globalId`), and writes messages through the same `insertMessage()`/`upsertThread()` the listener uses. One phone tap covers the whole run (message shards inherit the conversation-round confirmation). Non-friend 1-1 / OA conversations may stay keyed by their opaque id (no local name/id mapping without the `/api/gid/decrypt` fallback). **`--socket`:** the old best-effort server socket backfill (cmd 510/511), which usually returns empty — kept as a cheap probe, not a data path. It was the default until 2026-09-29; the inversion happened because `--days`, `--from`, `--messages-only` and `--shard-size` all shape the cmd 590 query and so were an error on the old default, which made a third of the command's own flags unusable without a flag. Passing any of them together with `--socket` is now the error instead. The restore runs on a live `listen`/`mcp` daemon's socket when one is up (same channel `sync` uses, no lock taken here, nothing stopped); otherwise it takes `daemon.lock` itself. The `--socket` cmd 510/511 probe is **not** routed — it is measured to answer empty, so there is nothing to hand off — and still refuses while a daemon runs, pointing at `zalo-agent sync` instead. All paths obey Zalo's one-web-session rule. `-w/--wait` bounds each phase (default 30s; the restore floors it at 600s, ten minutes, as Zalo's own clients wait, for the phone confirmation; only the phone's statuses 4 and 5 count as confirmation, so a phone that rejects, cancels, is busy, is low on storage or is signed out ends the sync with that reason and records nothing as synced). `-F/--force` skips the "already synced recently" debounce (which otherwise avoids re-pinging the phone). **`-d, --days <n>`** restores only the last *n* days (whole number ≥ 1) instead of full history. It sets the `from` bound on **both** the conversation round and the message rounds, so a short window returns fewer conversations, sends fewer ≤30-partition shards, and finishes far sooner — it is not just a per-conversation cut. **Default: full history, with no lower bound at all** — the `from` field of the cmd 590 query is sent as 0, so the phone is asked for everything it still holds. This was previously pinned at 2024-01-01, which silently meant an account with 2018 messages never had them requested and nothing in the output said so. **`--from <YYYY-MM-DD>`** sets an explicit lower bound and overrides `--days`; a date in the future, before Zalo existed, or unparseable falls back to full history rather than to a silently narrow window. Both are rejected with exit 1 when combined with `--socket`. Rejected with exit 1 when passed with `--socket`, since that path does not send the query. The freshness debounce is window-aware: each successful transfer records how far back it reached (`lastSyncOkFrom`), so a narrow run does not suppress a wider one (`--days 7` then a full sync ten minutes later still runs; the reverse is still skipped). Messages are stored with their real type: the payload's numeric `msgType` plus the attachment shape decide the row (`text`, `photo`, `video`, `file`, `gif`, `voice`, `doodle`, `sticker`, `link`, `location`, `card`, `event`, `group_event`, `poll_event`, `profile_card`, `deleted`, or `type_<n>` for a type this build has not seen — a `type_<n>` row carries no downloadable attachment, which is how voice notes (msgType 6) went unfetched until they were mapped), and the whole `meta` block — attachments, quote, mentions, TTL, bubble styling — is kept in `raw_data` as JSON alongside `cliMsgId`, so a synced row can anchor a reply the same way a listener-captured row can. The cmd 590 stream carries media *links*, never bytes, so once the messages are stored a `--transfer` run **downloads its attachments automatically** — a restored conversation whose photos are missing is only half restored. That fetch happens after the socket is closed and `daemon.lock` released (it needs neither), it is uncapped, and interrupting it is safe because `sync-media` resumes from whatever still has no `localPath`. A media failure never fails the run; the messages are already stored. **`-M, --messages-only`** skips the fetch for a fast history-only restore, and is rejected with exit 1 when combined with `--socket`. `has_attachment` marks rows carrying a fetchable file, and `sync-media` runs the same fetch on its own with filters. **Links are a media kind too** — Zalo's own media store has three tabs (image/video, file, link) — so a shared link is classified `link` and kept with its url/title/description/thumbnail, queryable via `getLinkMessages()`. It is deliberately kept out of the download queue (a link has no bytes) and kept distinct from OA notification cards and profile cards, which also carry an href; Zalo Web is equally narrow, indexing only `action: "recommened.link"`. A bare URL typed inside a plain-text message is not indexed as a link — Zalo Web does not index those either. The conversation round's own fields (`respondedByMe`, `lastGlobalId`, `lastClientId`) land on the `threads` row; a later listener write never clears them. **The socket is kept alive and a dropped one is resumed.** Zalo's own WebSocket heartbeat (`cmd 2/1`) runs on the interval the server hands out at login — measured at 180000 ms, which is the entire width of the phone wait — so the run sends the same frame on that interval for the whole socket window, as Zalo Web does, and counts the server's echoes, which is the only trace a bare `1006` (no close frame) leaves. `1006` is **not** in the server's own `close_and_retry_codes`, so zca-js never retries one: if the socket drops mid-restore the run pauses 2 s (Web's shortest retry), reconnects up to **three** times, first releases the dead socket's sessions with reason 3 and counts them again, and re-requests only the batches that never arrived, keeping everything already stored. Re-tapping the phone is the expensive part, so this is strictly better than failing — worst case the phone prompts a second time, which is what a manual re-run would have cost anyway, and the run says so explicitly when it happens. The server rejects a batch of more than 30. **A run remembers what it settled.** Per conversation, `zalo.db` records the window a restore settled (`sync_ranges`): a killed or partial run is finished by the next one, which asks only for the conversations that did not finish; a conversation that has moved on since is asked for only from where the last run stopped; a conversation the phone could not serve (or whose batch could not be downloaded) is asked for once more in the same run, and stays failed for the next if it fails again. | `sync-media [-T, --thread <id>] [-k, --kind <kinds>] [-n, --limit <n>] [-d, --days <n>] [-c, --concurrency <n>] [-m, --max-size <mb>] [--thumbs] [--dry-run]` | Download the attachments a mobile sync recorded. transfer-sync carries only CDN references, so this is the fetch step — and it needs **no phone confirmation and no socket**, so it can run while `listen` holds the account. Reads rows with `has_attachment = 1` and no `localPath`, writes to `accounts/<ownId>/media/<threadId>/<date>-<HH-mm>_<msgIdTail>_<name>.<ext>` — folders are thread IDs, never conversation names, with `media/_conversations.json` mapping ID to name, and records `localPath` back on the message. A Zalo CDN link that has aged out answers **HTTP 200 with a JSON error body** (`{"err_code":"1"}`) rather than failing, so the body is inspected; a lapsed link is retried once through `/api/message/renewlink` (cmd 12094), which only works while Zalo still holds the file. **That inspection is deliberately narrow: a 200 is the file unless the body identifies *itself* as an error** — a `content-disposition` naming a file settles it outright, otherwise only a JSON object carrying an error key, or a sub-1 KB body matching a known error phrase, counts as one. It used to treat any `text/…` response as guilty and fall through to a catch-all called "throttled", so every `.csv`/`.txt`/`.md`/`.log` attachment was downloaded in full, discarded, and reported as rate limiting, forever, at any `--concurrency`. **The summary reports what the response showed, not a cause inferred from it**: `throttled` counts only a 429/5xx or a server-busy body and is the one case advised to wait and lower `--concurrency`; `unknown` counts 403, an unrecognized body and a dead connection, names them by status (`HTTP 403 ×3`), and says a re-run may help but that only a fresh `sync --from <YYYY-MM-DD>` can hand back a new link — and not always, since the `urlToRenew` hints are mobile-only. Both retry identically; the split is reporting, not policy. `--kind` filters to `photo,video,file,gif,voice,audio,doodle` (default: all). `--dry-run` reports the plan without touching the network. A row that already has a `localPath` is never re-fetched. By default the run is limited to the window the **last mobile sync actually covered** (`lastSyncOkFrom`), since media outside it was never refreshed and its links are the likeliest to be dead — **`--all-history`** considers everything, and an explicit `--days` still wins. **`--prune <days>`** switches the command to cleanup: it deletes downloaded media attached to messages older than N days and **never touches message text**. A prune is recorded as a decision (`mediaPrunedAt`), not just a cleared `localPath` — otherwise the next `sync-mobile --transfer`, which fetches media by default, would re-download exactly what was deliberately deleted. Automatic fetches skip pruned media; **`--include-pruned`** deliberately brings it back, and downloading a file again clears the marker. **`--prune all`** (or `--prune <n> --all`) deletes every downloaded file regardless of age — a named mode rather than a very large cutoff, so no arithmetic slip on a date can become delete-everything. `--prune 0`, a negative, or anything non-numeric is rejected with a clear message before the account is even loaded. Always preview with `--dry-run`. **Deleting a conversation does not clean up after itself**: `conv delete` and `group disperse` call Zalo's API only — the local `messages`, `threads`, `board_items`, `reminders` and `reactions` rows all remain and their downloaded media stays on disk, never refreshed by a later sync because the conversation no longer appears in the conversation round. **`--prune-orphans`** reclaims the media of every such conversation in one pass (message text kept). Orphans are found two ways: a `leave`/`remove_member`/`block_member` event about **you** flags the thread (`threads.leftAt`) as it happens, and a transfer sync compares its conversation round against the cache and reports anything missing. `conv delete` and `group disperse` now flag the thread locally too. To remove the history as well, `conv forget <threadId>` or `conv forget --orphans` deletes the messages, reactions, board items, reminders, cloud index and media for those conversations — local only, Zalo is never contacted — and both support `--dry-run`. **`--timeout <seconds>`** (default 60) bounds a single download — `fetch()` has none of its own, and a server that sends headers then stops writing would otherwise block a worker indefinitely. |
| `sync-boards [-T, --thread <id>] [-n, --limit <n>] [-c, --concurrency <n>] [--no-reminders] [--no-boards]` | Sync notes ("Ghi chú"), pinned messages, polls and reminders ("Nhắc hẹn") into `board_items` / `reminders`. **None of this is in the message stream** — Zalo keeps it behind per-thread board endpoints (`/api/board/list` for groups, `/api/board/listReminder` and `/api/board/oneone/list` for reminders), so it needs its own pass. The conversation *events* announcing them do arrive as messages (`msgType` 24 for reminders, 26 for polls), but the objects themselves only exist here. One request per thread, so it runs at low concurrency with a pause between calls and defaults to the 200 most recent threads. Groups have boards; 1-1 conversations get reminders only. Needs no phone confirmation. |
| `sync-cloud [-p, --pages <n>] [-s, --page-size <n>] [-r, --resume <noiseId>] [--full]` | **The queue is applied, not just read** (v3.0): an `add` entry is recorded, a `remove` entry (a recall or a delete) deletes the item it names, a `del_thread` entry deletes a conversation's older items, a `reset_cloud` entry empties the index except the self chat; `temp` and `duplicate` entries change nothing. Each page is applied as it arrives, and **the place is saved after every page and kept when the walk is complete**, so the next run reads only what is new (a killed walk carries on from its last page); an explicit `--resume` wins over the saved place. **`--full`** walks from the top and, only once the server says it is done, deletes every local item no page listed (a sweep that corrects an index the incremental walks left stale; an unfinished full walk deletes nothing). Failures follow the web client's retry rules (server code 112, a dropped connection, an unreadable reply or an HTTP 4xx/5xx are retried after 0, 5, 5 and 10 s, a 4xx/5xx also moves to the next zCloud domain; -201 and every other code fail at once). A running `listen` or `mcp start` also does a bounded walk by itself when the server sends cmd 621, at most once in 30 minutes, never beside another stage, and **only after a person has run `sync-cloud` once** (the first walk reads the whole queue and is never started automatically). Walk the zCloud ("Cloud của tôi") media index into `cloud_items` — the reconciliation Zalo Web runs when the socket delivers a cmd 621 `mycloudMedia` event. Likewise: reactions, recalls, delivery receipts, board changes, read state and "you left this group" are written to `zalo.db` on every run, because most cannot be recovered afterwards. Reactions are the exception: the mobile-sync payload has no reaction field, but the socket serves the backlog on cmd 610/611, which `sync` (or `sync-reactions`) drains. **Read state from your other devices:** a conversation the account reads anywhere (the phone, Zalo Web, `conv read`) is reported on the socket as a `clearUnreads` row — cmd 504 (1-1) or 524 (group), and a field of every chat envelope and offline-queue page — which zca-js drops; the listener stores it as `conv_state.lastReadMsgId`/`lastReadTs`, a watermark that only moves forward (one read is reported more than once, and an offline page can arrive after a newer push). Retries wait 1 s, doubling to 5 min, and survive a restart or crash; a payload the receiver refuses as malformed (400, 413, 422) is dead-lettered instead, as is any event still undelivered after `ZALO_WEBHOOK_MAX_AGE` (default 24h, at least 1m). `ZALO_WEBHOOK_BATCH_SIZE[_<ownId>]` (1–100, default 1) sends that many queued events per POST as `{"event":"batch","accountId":…,"count":N,"events":[…]}`; a single event is always the plain payload. Both produce the same tombstone the phone keeps, record the kind in `raw_data.removedAs`, preserve `cliMsgId`, and take the downloaded media with them (`has_attachment` cleared, `mediaPrunedAt` set, file deleted). A mobile sync restores the same event under the phone's own clientId, landing 1–4 ms from the live time (measured), and replaces the placeholder one-for-one; a live event a sync already holds writes nothing. Polls and reminders are left to their own message frames. **Live sender/conversation name cache refresh:** when a live DM or group message arrives or `sync` runs, cached sender and thread names in `zalo.db` are refreshed automatically without overwriting deliberate user aliases. Tracks connection gaps: after a reconnect, and on startup for the time since the last known-connected moment (anything of a second or more), the window is filed in `sync_gaps`. **Then it self-heals, the way Zalo Web does on every connect:** it asks Zalo's offline message queues (`510_1` for 1-1, `511_1` for groups) on its own socket for everything after the newest message it stored, pages until the server says there is no more, and writes what comes back insert-if-absent (`raw_data.src: "offline"`, printed as `[catch-up]`). No phone tap is involved, and live traffic keeps arriving and being stored meanwhile. A gap is resolved only for the window that pull actually covered. A queue the server reports as dropped (`evict`) or reset is recorded as a gap of its own, and whatever stays pending is printed with the exact run that restores it — `zalo-agent sync --from <YYYY-MM-DD>`, dated from the gap's own start so the window is guaranteed to cover (and resolve) it. That run is the phone-backed `transfer-sync-v2`, which the daemon never starts on its own: it needs a tap on "ĐỒNG BỘ NGAY". Measured live 2026-09-30: a 75-minute outage came back in full from both queues with no prompt on the phone; under `--no-self-heal` a message sent during a drop stayed missing, and the next self-heal run recovered it and closed the gap the opt-out run had left pending. The cursor is the newest *stored* message, so a live message stored during a `--no-self-heal` run moves it past anything not yet recovered — that part stays pending for `sync` rather than being claimed. `--no-self-heal` records and reports gaps without the catch-up. After the message queues the same step replays the control events missed while away (group and friend events, unread marks set on another device, transcribed voice messages) from the saved control cursors, as if they had just been pushed; it asks only with a saved cursor, acknowledges nothing, and leaves the end-to-end encryption queues (515, 517, 518) alone. **Start-up spreading** (both daemons, off by default): `ZALO_START_JITTER[_<ownId>]` (seconds, 0–600) waits a random time up to that long, with the daemon lock already held, before logging in; `ZALO_LOGIN_SLOTS[_<ownId>]` (0–64, 0 = no cap) lets at most that many daemons on the machine be logging in and loading their lists at once, through files in `<config dir>/login-slots/` (the slot is held from before login until the lists are loaded; a daemon over the cap waits, then goes ahead anyway after `ZALO_LOGIN_SLOT_WAIT` seconds, default 900; a slot whose daemon died, or that was held over 300 s, is reclaimed). The daemon also **performs** the phone-backed restore when `zalo-agent sync` asks it to, on the socket it already holds (one stage at a time: the catch-up waits behind a running stage), and a completed `sync` resolves the gap via `recordRestoreSuccess()`. **Delivered receipts (default on):** every received message Zalo can identify — your own echoes included — is acknowledged with `deliveredv2`, as Zalo Web does, batched per conversation (150 ms, up to 50 per call). Frames without a usable `msgId`/`cliMsgId`/thread id are skipped, and only `message` events are acknowledged at all; removal frames are not. It is best-effort: failures go to stderr and never affect storage or output. `--no-delivered-receipts` turns it off. **Seen receipts are never sent automatically** — only `conv read` sends one. |

## Official Account — `oa` (official REST API v3.0, ~32 commands)

Completely independent from the personal zca-js account: separate OAuth credentials, separate storage (`~/.zalo-agent/oa-credentials.json`, note: **no `-cli` suffix** — different directory from personal `~/.zalo-agent-cli/`), no unofficial-API disclaimer shown. Multi-OA supported everywhere via `--oa-id <id>` (default: `"default"`).

### Auth & Setup

| Command | Description |
|---------|-------------|
| `login --app-id <id> --secret <key> [-p, --port <port>] [--callback-host <host>] [--oa-id <id>]` | OAuth login: opens a browser to the Zalo consent screen and starts a local callback server (default port 3456) to receive the auth code. `--callback-host <url>` switches to VPS/headless mode: binds the callback server to `0.0.0.0` instead of `127.0.0.1`, skips auto-opening a browser (prints the URL to open manually on a local machine instead), and uses that host for the redirect URI. 2-minute timeout. |
| `refresh [--oa-id <id>]` | Refresh the access token using the stored refresh token. |
| `setup <access-token> [--oa-id <id>]` | Manually set an access token, bypassing OAuth entirely (e.g. copied from another machine). |
| `whoami [--oa-id <id>]` | Show the OA's profile: name, ID, description, follower count, and — when Zalo returns them — its type, package (with its valid-through date) and linked-ZCA flag. The package decides which APIs answer: a `-224` means it is too low for that call. |
| `init [--oa-id <id>] [--app-id <id>] [--secret <key>] [--tunnel ngrok\|cloudflared\|none] [--webhook-url <url>] [--verify-code <code>] [-p, --port <port>] [--skip-webhook] [--skip-login]` | **Guided setup wizard** — works both interactively (human, prompts at each step) and non-interactively (agent mode, triggered automatically whenever `--app-id` is passed). Walks through: (1) save app-id/secret, offering to reuse existing saved creds; (2) OAuth login (skippable with `--skip-login`, or auto-skipped in agent mode if a token is already saved) and profile verification; (3) an interactive-only prerequisite checklist (callback URL, API enablement, permissions at developers.zalo.me); (4) webhook exposure — `--skip-webhook` skips entirely; `--webhook-url` saves a pre-existing URL (VPS/n8n/etc., optionally with `--verify-code`); otherwise picks a tunnel type (interactively prompted 1-5, or `--tunnel` non-interactively, defaulting to `ngrok` in agent mode) among **ngrok**, **cloudflared**, **none**, plus two interactive-only paths (`n8n`, `own server`) that just prompt for a URL to save. For ngrok/cloudflared it checks the CLI tool is installed, starts a local webhook listener on `-p/--port` (default 3000), starts the tunnel, and saves the resulting `<tunnelUrl>/webhook` as the webhook URL; (5) prints a quick-reference summary (JSON in `--json` mode). |

### Webhook Listener — `oa listen`

| Command | Description |
|---------|-------------|
| `listen [-p, --port <port>] [-s, --secret <key>] [--no-verify] [-e, --events <list>] [--path <path>] [--verify-domain <code>]` | Start a local HTTP webhook server for OA events. `-p/--port` default 3000. `-s/--secret` enables **HMAC-SHA256 MAC verification** (timing-safe compare) against the `X-Zevent-Signature`/`mac` header — a warning is printed if no secret is given. `--no-verify` explicitly disables verification even with a secret set. `-e/--events` filters to a comma-separated subset (default `all`) of the 57 events Zalo documents (listed in `oa-command-reference.md`, source `OA_WEBHOOK_EVENTS` in `src/commands/oa-listen.js`); a name Zalo does not document prints a warning at start, since that filter can never match. `user_send_gif`, `user_click_button` and `user_click_link`, listed before 2.0.0, are not Zalo events. The listener **answers 200 as soon as an event is accepted**, before printing it — Zalo wants it within 2 seconds, redelivers, and eventually disables the webhook — and a redelivery (Zalo's `num_retry` header) is flagged as such, `_num_retry` in `--json`. `--path` changes the webhook URL path (default `/webhook`). `--verify-domain <code>` serves the Zalo domain-verification meta tag/HTML file needed at `developers.zalo.me`. Handles Zalo's `hub.challenge` GET verification automatically. Body size capped at 1MB. |
