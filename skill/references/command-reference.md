# zalo-agent CLI — Full Command Reference

Exhaustive reference for every command, subcommand, and flag `zalo-agent` exposes. Generated by reading every file in `src/commands/` and `src/mcp/mcp-tools.js` directly (not from prior docs), current as of v3.0.0.

## Global Behavior

- **`--account <id>`** (global flag, works before or after any command; env: **`ZALO_ACCOUNT`**) — pin this invocation or daemon (`listen`, `mcp start`, or any one-shot CLI command such as `msg send`, `conv recent`, `sync`, `whoami`, `status`, `logout`) to an exact, full numeric registered account ID without changing the shared `active` entry in `accounts.json`. Omitting the flag uses the active account (and for `listen`/`mcp start`, pins that active account at startup across reconnects and retries). Names, partial IDs, and empty values are refused; an unregistered ID fails immediately before authentication. For `listen` and `mcp start`, the selected account's lock is acquired before authentication and a mismatched authenticated UID is rejected. Running multiple live accounts simultaneously is done by running one `listen` or `mcp start` process per `--account <id>` (and passing `--account <id>` on concurrent CLI invocations). See [English](../../docs/account-pinning.md) / [Tiếng Việt](../../docs/account-pinning.vi.md).
- **Alias first, everywhere a person is named (3.0):** every command, `--json` reply, MCP reply, webhook payload, `listen`/daemon line and search result names a person by **the alias the account owner set for them** (as Zalo shows it), then their Zalo name, then their display name, then the uid (`src/core/contact-names.js`). The existing name field carries that value (`senderName` on a message and on `replyTo`, `dName` on a `listen` message event and on a group event's `updateMembers[]`, `displayName` on a friend/profile/member, `dpn` on `group pending`, `inviterName` on an invitation); beside it, **`senderAlias`/`alias`** (the alias or `null`) and **`senderZaloName`/`zaloName`** (the name before the alias; on a message, the name it carried). Stored rows are never rewritten: `zalo.db` keeps the name each message carried, and the alias snapshot sits in its own table (`user_aliases`), which `db export` carries too. A 1-1 is titled by the alias at display time; a group's title never is. A `listen`/`mcp` daemon reads the alias list at start, again 1.5 s after each `alias` control (an alias set, changed or removed on any device) and every 30 minutes, keeps the snapshot in `zalo.db` for one-shot commands (`msg search`, `conv list`, mentions), and retitles the stored 1-1s whose alias changed. A `profile` control (`update`, the account's own name changed elsewhere) rereads the account's name. `listen`'s human lines now name the sender of an incoming message (`← [GR] [threadId] Minh Sales: text`), the friend-request sender, the typer, the reactor (`by Name (uid)`) and a group event's members. `msg history`, MCP history and buffered-message reads also add `senderDisplayName` plus `senderDisplayNameSource` (`alias`, `phonebook`, `zalo`, `display`, `uid`), the current label read fresh from Zalo. CLI text history prints the current label. Sync refreshes cached DM titles even outside the restored message window without changing activity timestamps. See [English](../../docs/current-user-names.md) / [Tiếng Việt](../../docs/current-user-names.vi.md) for failure behavior and restoration limits.

- **`--json`** (global flag, works before any command) — machine-readable JSON output for every command. Also suppresses the startup disclaimer and the "Note:"/`info()` lines that would otherwise print to stdout.
- **`--env-file <path>`**, **`--config-dir <dir>`**, **`--credentials-dir <dir>`**, **`--data-dir <dir>`**, **`--media-dir <dir>`**, **`--oa-dir <dir>`** (global flags, work before any command) — load a `.env` file (`--env-file` / `ZALO_ENV_FILE`, plus automatic loading of `./.env` and `<CONFIG_DIR>/.env`) and override the default `$HOME`-based storage roots so config (`accounts.json`, `mcp-config.json`), personal session credentials (`cred_<ownId>.json`), per-account database & runtime state (`<ownId>/zalo.db`, `daemon.lock`, `daemon-channel.json`), downloaded media (`<threadId>/`), and Official Account credentials (`oa-credentials.json`) can live on separate volumes or mounts in production. Equivalent to setting `ZALO_CONFIG_DIR`, `ZALO_CREDENTIALS_DIR`, `ZALO_DATA_DIR` (or `ZALO_DB_DIR`), `ZALO_MEDIA_DIR`, and `ZALO_OA_DIR`; CLI flags take precedence over environment variables, which take precedence over `.env` files.
- **`-V, --version`** — print the installed version.
- **`-h, --help`** — help for the CLI or any subcommand (`zalo-agent <group> --help`).
- **Disclaimer**: on every command *except* `oa` commands and JSON mode, the CLI prints: "This tool uses unofficial Zalo APIs — your account may be banned. Use at your own risk." (VN translation included). `oa` commands are exempt because they use the official Zalo OA REST API.
- **Auto-login**: before running any command, the CLI auto-logs-in the target account (`--account <id>` / `ZALO_ACCOUNT` if set, otherwise the active account in `accounts.json`) — *except* for `login`, `account`, `help`, `version`, `update`, `oa`, `listen`, and `mcp` (these manage their own auth or don't need one).
- **Update check**: a non-blocking background check against the npm registry runs before every command except `update` itself. It is silently skipped when stdout is not a TTY (piped/scripted use), in `--json` mode, or when the env var `ZALO_AGENT_NO_UPDATE_CHECK` is set. It only ever warns when a genuinely *newer* semver version is published — a local dev build ahead of npm (e.g. `2.0.0-dev` vs published `1.0.7`) will not trigger a false "update available"/downgrade warning.
- **Hidden chats** follow Zalo's own rule: a hidden conversation is left out of `conv recent`, `conv pinned`, `msg search`, `msg history` and `listen` output unless the command is run with `--include-hidden` (`conv recent`, `msg history`, `listen`), which asks for the PIN at a prompt that does not echo, or reads it from standard input with `--pin-stdin`. **The PIN is never a command-line argument**, never printed, stored or logged: it is checked against the hash Zalo hands the session, in memory. Without a terminal and without `--pin-stdin` a command that needs it prints `{"error", "pinRequired": true, "retryWith": "--pin-stdin"}` and exits **2**. Six wrong PINs start a growing back-off (30 s, doubling, at most an hour), kept per account in `hidden-pin-lockout.json` (counts and times only). A command with no session (`msg search`) reads the hidden ids from `hidden-threads.json` in the account folder, which every read of the list and the listener keep current.
- **Confirmation guard** (`src/core/confirm-guard.js`): the destructive commands Zalo's own apps ask about first act only with **`-y, --yes`**. **`--dry-run`** says what the command would do, sends nothing and exits 0. With neither, **nothing is sent and the command exits `2`** (distinct from a failure's `1`), printing `✗ Not done: this would <what> [— this cannot be undone]. Re-run with --yes, or --dry-run to preview.`; with `--json`, stdout is `{"error":"Not done: confirmation needed: <what>","confirmationRequired":true,"action":"<command>","wouldDo":"<what>","target":{…},"irreversible":true|false,"retryWith":"--yes"}`. The check runs before auto-login, so a refused or previewed command never touches the session. There is no global off switch. Guarded: `group leave`, `remove-member`, `remove-admin`, `transfer-owner`, `block-member`, `disable-link`, `disperse`, and `settings` only when it turns join approval off (`--no-join-appr`); `friend remove`, `block`, `reject`, `undo-request`; `msg undo`, `delete` (with or without `--everyone`); `conv delete`, `hidden-pin-reset`, `unhide`, `forget` (keeps its own `--dry-run`, which lists what would be removed); `poll lock`; `reminder remove`; `label update` only when the new list leaves a label out (it reads the current list first); `catalog delete`, `delete-product`; `bank remove`; `auto-reply delete`; `quick-msg remove`; `profile delete-avatar`; `logout` (every variant); `account remove`, `export` (it writes the login out in plaintext); `mcp webhook purge`; `db export` only with `--plaintext` (an encrypted or `--password` copy is not asked about), `db purge` (keeps its own `--dry-run`, which counts); `fleet purge`; `cloud apply` (keeps its own `--dry-run`, which prints the plan); `presence resume`. `write run` keeps its own `--yes`/`--dry-run` and its unconfirmed exit is `2` too. `msg pin` is not guarded: Zalo's own apps ask only when the pin would replace an existing one, and knowing that takes a read.
- **Exit codes** (3.0): `0` done, `1` failed (most commands exited 0 on failure before 3.0), `2` confirmation needed (the guard below) or a PIN needed without a terminal, `3` an always-on daemon (`listen` in the foreground, stdio `mcp start`, or `presence.mode: "always-on"`) was kicked by another session of the same login, `4` Zalo keeps refusing the saved login (for a daemon only with `ZALO_EXIT_ON_SIGNED_OUT=1`: by default it stays up `signed_out`). An on-demand daemon that is kicked stays up `yielded` instead of exiting 3. `--json` always prints one JSON object or array, and a failure leads with `error`.
- **Thread type flag** (`-t, --type <n>`), used across almost every messaging/thread command: `0` = User/DM (default), `1` = Group.

| `login [-p, --proxy <url>] [-n, --name <label>] [--qr-url] [-q, --qr-port <port>] [--public-url <url>] [--credentials <path>] [--sync \| --no-sync] [--sync-days <n>] [--verbose]` | Login via QR scan, or from an exported credentials file (`--credentials`, skips QR entirely). **Device id:** Zalo keeps the offline queue per device (imei), and a QR re-login keeps the account's device id: the active account's saved user agent is presented again, and an account that confirms the QR with a device id saved for that user agent logs in with it. A first login here, an account whose saved login is gone (`logout` deletes it) or unreadable, or another account gets a new device id; the login says which (`Device: the same device id ...` or `Device: a new device id ... (<why>)`; `--json`: `newDevice` and `device` in `login_success`), and the saved credentials record since when the id is in use (`deviceSince`), so a daemon never claims coverage from before it. **What the phone shows (measured):** each QR login adds a new entry to the phone's device list and the older entries for this login are logged out, but the offline queue survives because the device id is kept. **One web login per account:** Zalo keeps one web login per account, so a QR login into Zalo in a browser anywhere else logs this one out (a running daemon then stays up `signed_out`, see `listen`); use the phone or the Zalo desktop app beside the server, not a browser. **The phone's "sync messages to this device" box** (QR login only): after the login the command always reads the phone's `transfer_after_login` control and says whether it was ticked. It reads each control queue the account's handshake names (`603_1`, `603_0`): from the cursor `listen` saved, page by page while Zalo says there is more, then from the queue's start if the cursor did not find it (a re-login that keeps the device id keeps the queue, and the offer is at its end). **`--verbose`** lists the queues read (from where, pages, how each read ended) and every control seen (queue, act type, act, `pc`, whether it had a key, age; never the key); with `--json` they are `pulls` and `controls` in the `login_auto_sync` event. **Ticked:** the history is restored at once with the short-lived key the phone sends (no tap; `--sync-days <n>` limits it to the last N days). **`--no-sync`** only reports. **Not ticked**, ticked more than two minutes before the socket was up, or an offer meant for the desktop app (`pc` not 0): nothing is started, and a new device is told the run that restores what it lacks (`zalo-agent sync --from <date>`, from the last time the account was connected here, or `zalo-agent sync` on a first login). `--sync` is the default's older spelling, kept for scripts. A `listen`/`mcp` daemon holding the account: the offer is not read (a second socket would fight the daemon) and the command is printed instead. `--json` adds a `login_auto_sync` event (`status`: `restored`, `declined`, `none`, `late`, `other-client`, `same-device`, `daemon-running`, `unknown`, `failed`; `command` when one applies). A local HTTP server for viewing the QR in a browser always starts (default port 18927, override with `--qr-port`); the page binds loopback (`127.0.0.1`) unless `--qr-url` offers it to the LAN, or `--public-url` serves it as a one-time `<publicUrl>/zalo/qr/<token>` page behind a reverse proxy; from a VPS without either, reach it through an SSH tunnel. During the QR flow the CLI surfaces every QR event: generated (shows QR + starts HTTP server), **scanned** (prints who scanned it — name + avatar URL — and prompts to confirm on phone), **declined** (login fails immediately, does not hang until the 60s timeout), and **expired** (a fresh QR: at once with `--json` or no terminal, on request at a terminal). **`--public-url <url>`** (or `ZALO_MCP_PUBLIC_URL`, or `publicUrl` in `mcp-config.json`; not the deprecated `--issuer-url` names) prints the QR page as `<url>/zalo/qr/<one-time token>` (image at `.../qr.png`) for a reverse proxy that routes `/zalo/qr/` to the QR port: a random 128-bit token that lives while a code is on screen and ends with the login, every answer `no-store` with a CSP allowing only the page's own image, style, script and polls, no referrer, no framing; `--json` puts it in the `qr_server` event's `publicUrl`/`publicImageUrl`. `https`, or `http` on localhost only; a value that breaks a rule stops the command. Without it the page stays `http://localhost:<port>/qr`. |
| `logout [--purge] [--delete-history] [--no-remote] [--keep-session]` | A real logout on this device: signs the device out at Zalo the way Zalo's own apps do — six calls (a one-time token from `id.zalo.me`, the profile `deactive` call, the `v2` logout, `id.zalo.me`'s own logout, the `setsid` hops, the login page) — then tries the saved login once, and reports the device as signed out only when Zalo refuses it (a saved login that still works is a warning that points at the phone's list of logged-in devices). It then **deletes the saved credentials**, so the next command needs a new QR login. The chat cache is kept for that next login. `--keep-session` does only what `logout` did before v3.0: it ends this process's session *key* (the production `GET /api/login/logOut`, then `logoutV2()`), which leaves the saved login valid at Zalo and the device in the phone's list until it is removed there; the credentials are still deleted. `--no-remote` skips every server call (the credentials are still deleted). `--delete-history` also deletes the local chat cache (`zalo.db` + downloaded media), matching Zalo's own "Delete chat history on logout" checkbox. `--purge` fully removes the account from this machine: wipes the *entire* per-account data directory (db, media, sync keys, daemon.lock — same as `account remove`), deletes the saved credentials, and removes the account from the registry. All three refuse to delete anything while a `listen`/`mcp` daemon holds the account's lock, naming its PID — stop it first. Stopping and restarting a daemon is not a logout: the credentials stay, it logs back in, and self-heal catches up what arrived meanwhile. |
| `status` | Show current login state: logged in y/n, own user ID, active account name/proxy. |

| `update` | Self-update: runs `npm install -g @ardennguyen/zalo-agent-cli@latest`. |
| `sync [-F, --force] [-d, --days <n>] [--from <date>] [-w, --wait <seconds>] [--no-messages] [--no-reactions] [--no-conv-state] [--no-boards] [--no-cloud] [--no-media] [--media-limit <n>] [--no-removals] [--shard-size <n>] [--full-resync] [--plan]` | **One run that pulls every kind of message state** — the command to use by default. Reactions, pinned conversations, notes, polls and reminders are all state of the messages and conversations; they used to need five separate commands, two of which each opened their own socket and took their own lock, so a full refresh evicted another Zalo session twice. `sync` runs them as stages of one process with one lock and one exit code: **(1)** open the WebSocket once, with one live-store tap for the whole window so nothing arriving during the run is lost; **(2)** the message restore (cmd 590/591) — the **only phone prompt, at most once per run** — alone, exactly as `sync-mobile` runs it; **(3)** the reaction backlog drain (cmd 610/611) on the same socket. (A first version drained reactions concurrently with the restore; the restore then lost its socket with close 1006 at batch 0 on both live attempts, while the same 30-day window restored 11,324 messages through `sync-mobile` minutes later.) **(4)** retry reactions whose message was not stored when they arrived; **(5)** close the socket, wait for it to actually close, release the lock; then the REST stages **(6)** pinned and unread conversations into `conv_state`, **(7)** boards (notes, pinned messages, polls, reminders), **(8)** the zCloud index, **(9)** media last. The socket is opened once and never restarted, because stopping the listener resets it and the socket's own onclose resets it again later — a stop-then-restart between stages races and nulls the new socket. **A running `listen`/`mcp` daemon is never evicted, and no longer has to be stopped**: when one is up, the socket stages (2)–(4) run **on that daemon's socket** over the loopback channel it advertises in `daemon-channel.json`, streaming their progress back so the run prints exactly as it would locally, while the daemon keeps capturing live traffic throughout. This process opens no WebSocket and takes no lock; the REST stages run here as always. The old answer — stop the daemon, sync, restart it — opened a fresh coverage gap of its own (~70s between the restore's snapshot and the daemon coming back, unrepairable since `pullMobileMsg` answers empty). The phone tap is unchanged: routing removes the second WebSocket, not the confirmation, and the daemon never starts a sync on its own. A daemon that is up but published no usable channel still causes the socket stages to be skipped with that reason. `--plan` shows the routing in the transport column (`socket→daemon`) and as `viaDaemon` in `--json`. The cloud stage follows the same rule for its own reason (two walkers of one queue write its saved place out of order): with a daemon that runs the `cloud` stage up, `--plan` shows it as `rest→daemon`, says so in a line, and sets `cloudViaDaemon` in `--json`; with a process holding the account that cannot run it, the stage is shown skipped with the reason. The message restore is debounced exactly as `sync-mobile --transfer` is (`--force` to override); the reaction backlog is not, since it never prompts the phone — `--no-reactions` together with a fresh restore opens no socket at all. `--plan` prints each stage's order, transport, whether it would run and why, and exits without sending anything. Ends with a one-line-per-stage summary (`ok`, `partial`, `skipped`, `unavailable`, `unconfirmed`, `failed`); with `--json` that summary is the single JSON document on stdout. Exits 1 only if a stage failed — an account without zCloud reports the cloud stage `unavailable`, not failed. Stage tuning (`--pages`, `--kind`, `--prune`, …) stays on the per-stage commands below, which remain for re-running a single stage. **Pinned and unread, as measured live:** pinned ids arrive prefixed with the thread kind (`g<groupId>`, `u<userId>`) and are stripped; unread-mark ids arrive as JSON *numbers*; the engine keeps every digit of a 19-digit thread id. An id an older version stored rounded (`4123456789012345678` → `4123456789012346000`) is matched to the one cached thread that rounds to the same value, and an ambiguous match is reported, never guessed. **The socket is kept alive and a dropped one is resumed.** Zalo's own WebSocket heartbeat (`cmd 2/1`) runs on the interval the server hands out at login — measured at 180000 ms, which is the entire width of the phone wait — so the run sends the same frame on that interval for the whole socket window and counts the server's echoes, which is the only trace a bare `1006` (no close frame) leaves. `1006` is **not** in the server's own `close_and_retry_codes`, so the server's reconnect table never retries one: if the socket drops mid-restore the run pauses 2 s (Zalo's shortest retry), reconnects up to **three** times, first releases the dead socket's sessions with reason 3 and counts them again, and re-requests only the batches that never arrived, keeping everything already stored. Sessions are requested up front in waves of up to 30 (the phone stops serving at about 32 open together) and a wave is released one session at a time once it is stored; a session the phone leaves incomplete and idle for a minute fails alone and its conversations are asked for once more at the end. Re-tapping the phone is the expensive part, so this is strictly better than failing — worst case the phone prompts a second time, which is what a manual re-run would have cost anyway, and the run says so explicitly when it happens. A failure now distinguishes **the socket died** from **the phone never answered**: they need opposite things from you. **`--shard-size <n>`** (1–30, default 30) sets how many conversations go in each message batch; fewer means more, smaller batches, so the first one comes back sooner and less is lost to a drop, at the cost of more sync sessions. The server rejects a batch of more than 30. **A run remembers what it settled.** Per conversation, `zalo.db` records the window a restore settled (`sync_ranges`): a killed or partial run is finished by the next one, which asks only for the conversations that did not finish; a conversation that has moved on since is asked for only from where the last run stopped; a conversation the phone could not serve (or whose batch could not be downloaded) is asked for once more in the same run, and stays failed for the next if it fails again. Every request is acknowledged by Zalo (10 s, retried), every session is released with the reason that fits how the run ended, and sessions a dead run left open are released as outdated at the next start. A run that did not settle its whole window records no success, so the "synced recently" shortcut never hides unfinished work, and does not apply while a conversation range is unfinished. **`--full-resync`** forgets all of it and asks for every conversation in full. **Ctrl+C** during the restore stops it cleanly: what already arrived is kept, the sessions open on the phone are released (as cancelled), nothing is recorded as settled, and the result says `cancelled`; a second Ctrl+C quits at once (exit 130). **`--media-limit <n>`** caps the attachments one run downloads (two at a time; default: all of them). What is left stays pending, and the run says how many, for `sync-media` to continue. **No stage stops at a page count (3.0):** the reaction drain, the zCloud walk, the boards pass and the media stage run until the server says there is no more, or until its cursor stops moving between two pages (the runaway sign, reported as `stalled`/`partial`); the boards stage covers every cached conversation, and a restore's non-friend name refresh asks for every non-friend DM peer in requests of 500, stopping on Zalo's 221 (`nameRefresh` in the result says how many were left; those ids are parked for an hour). |
| `sync-mobile [--socket] [-F, --force] [-d, --days <n>] [--from <date>] [-M, --messages-only] [-w, --wait <seconds>] [--shard-size <n>] [--full-resync]` | Restore message history from the phone into the local cache (`zalo.db`). **This is the real, phone-backed restore (transfer-sync-v2, socket cmd 590/591), and it is now the default — no flag needed.** `-t/--transfer` is still accepted and ignored, so scripts and older docs that pass it keep working. It sends ONE sync request the owner confirms on their phone (tap "ĐỒNG BỘ NGAY"), enumerates every conversation (conversation round), then requests message history in shards of ≤30 partitions (server cap), decrypts each batch with Zalo's `libzproto` WASM (fetched+cached from Zalo's CDN on first run), Zstd-decompresses, protobuf-decodes, maps each opaque conversation id to the real numeric threadId + name via the friend/group lists (both expose `globalId`), and writes messages through the same `insertMessage()`/`upsertThread()` the listener uses. One phone tap covers the whole run (message shards inherit the conversation-round confirmation). Non-friend 1-1 / OA conversations may stay keyed by their opaque id (no local name/id mapping without the `/api/gid/decrypt` fallback). **`--socket`:** the old best-effort server socket backfill (cmd 510/511), which usually returns empty — kept as a cheap probe, not a data path. It was the default until 2026-09-29; the inversion happened because `--days`, `--from`, `--messages-only` and `--shard-size` all shape the cmd 590 query and so were an error on the old default, which made a third of the command's own flags unusable without a flag. Passing any of them together with `--socket` is now the error instead. The restore runs on a live `listen`/`mcp` daemon's socket when one is up (same channel `sync` uses, no lock taken here, nothing stopped); otherwise it takes `daemon.lock` itself. The `--socket` cmd 510/511 probe is **not** routed — it is measured to answer empty, so there is nothing to hand off — and still refuses while a daemon runs, pointing at `zalo-agent sync` instead. All paths obey Zalo's one-web-session rule. `-w/--wait` bounds each phase (default 30s; the restore floors it at 600s, ten minutes, as Zalo's own clients wait, for the phone confirmation; only the phone's statuses 4 and 5 count as confirmation, so a phone that rejects, cancels, is busy, is low on storage or is signed out ends the sync with that reason and records nothing as synced). `-F/--force` skips the "already synced recently" debounce (which otherwise avoids re-pinging the phone). **`-d, --days <n>`** restores only the last *n* days (whole number ≥ 1) instead of full history. It sets the `from` bound on **both** the conversation round and the message rounds, so a short window returns fewer conversations, sends fewer ≤30-partition shards, and finishes far sooner — it is not just a per-conversation cut. **Default: full history, with no lower bound at all** — the `from` field of the cmd 590 query is sent as 0, so the phone is asked for everything it still holds. This was previously pinned at 2024-01-01, which silently meant an account with 2018 messages never had them requested and nothing in the output said so. **`--from <YYYY-MM-DD>`** sets an explicit lower bound and overrides `--days`; a date in the future, before Zalo existed, or unparseable falls back to full history rather than to a silently narrow window. Both are rejected with exit 1 when combined with `--socket`. Rejected with exit 1 when passed with `--socket`, since that path does not send the query. The freshness debounce is window-aware: each successful transfer records how far back it reached (`lastSyncOkFrom`), so a narrow run does not suppress a wider one (`--days 7` then a full sync ten minutes later still runs; the reverse is still skipped). Messages are stored with their real type: the payload's numeric `msgType` plus the attachment shape decide the row (`text`, `photo`, `video`, `file`, `gif`, `voice`, `doodle`, `sticker`, `link`, `location`, `card`, `event`, `group_event`, `poll_event`, `profile_card`, `deleted`, or `type_<n>` for a type this build has not seen — a `type_<n>` row carries no downloadable attachment, which is how voice notes (msgType 6) went unfetched until they were mapped), and the whole `meta` block — attachments, quote, mentions, TTL, bubble styling — is kept in `raw_data` as JSON alongside `cliMsgId`, so a synced row can anchor a reply the same way a listener-captured row can. The cmd 590 stream carries media *links*, never bytes, so once the messages are stored a `--transfer` run **downloads its attachments automatically** — a restored conversation whose photos are missing is only half restored. That fetch happens after the socket is closed and `daemon.lock` released (it needs neither), it is uncapped, and interrupting it is safe because `sync-media` resumes from whatever still has no `localPath`. A media failure never fails the run; the messages are already stored. **`-M, --messages-only`** skips the fetch for a fast history-only restore, and is rejected with exit 1 when combined with `--socket`. `has_attachment` marks rows carrying a fetchable file, and `sync-media` runs the same fetch on its own with filters. **Links are a media kind too** — Zalo's own media store has three tabs (image/video, file, link) — so a shared link is classified `link` and kept with its url/title/description/thumbnail, queryable via `getLinkMessages()`. It is deliberately kept out of the download queue (a link has no bytes) and kept distinct from OA notification cards and profile cards, which also carry an href; Zalo itself indexes only `action: "recommened.link"`. A bare URL typed inside a plain-text message is not indexed as a link — Zalo does not index those either. Sessions are requested up front in waves of up to 30 (the phone stops serving at about 32 open together) and a wave is released one session at a time once it is stored; a session the phone leaves incomplete and idle for a minute fails alone and its conversations are asked for once more at the end. Re-tapping the phone is the expensive part, so this is strictly better than failing — worst case the phone prompts a second time, which is what a manual re-run would have cost anyway, and the run says so explicitly when it happens. A failure now distinguishes **the socket died** from **the phone never answered**: they need opposite things from you. **`--shard-size <n>`** (1–30, default 30) sets how many conversations go in each message batch; fewer means more, smaller batches, so the first one comes back sooner and less is lost to a drop, at the cost of more sync sessions. The server rejects a batch of more than 30. **A run remembers what it settled.** Per conversation, `zalo.db` records the window a restore settled (`sync_ranges`): a killed or partial run is finished by the next one, which asks only for the conversations that did not finish; a conversation that has moved on since is asked for only from where the last run stopped; a conversation the phone could not serve (or whose batch could not be downloaded) is asked for once more in the same run, and stays failed for the next if it fails again. Every request is acknowledged by Zalo (10 s, retried), every session is released with the reason that fits how the run ended, and sessions a dead run left open are released as outdated at the next start. A run that did not settle its whole window records no success, so the "synced recently" shortcut never hides unfinished work, and does not apply while a conversation range is unfinished. **`--full-resync`** forgets all of it and asks for every conversation in full. **Ctrl+C** during the restore stops it cleanly: what already arrived is kept, the sessions open on the phone are released (as cancelled), nothing is recorded as settled, and the result says `cancelled`; a second Ctrl+C quits at once (exit 130). |

**Env vars:** `ZALO_ACCOUNT` (or `--account <id>`) pins the target registered numeric account ID for the command or daemon without changing the global active entry in `accounts.json`. `ZALO_AGENT_NO_UPDATE_CHECK` (any value) disables the background update-version check entirely. `ZALO_API_VERSION` sets the protocol version announced to Zalo (`zpw_ver` / `client_version`), on both the HTTP calls and the WebSocket URL; the default is 695, the value Zalo currently expects, and an older value such as `685` rolls back. The state-changing endpoints of Zalo's API that have no command of their own (plan track S, 6.2). **Every one changes something on the account.** Each is built to Zalo's wire format (`src/zalo/writes.js` lists host, path and body) and tested on the wire; 26 of the 27 were then seen to work on a live account (2026-10-27 and 2026-10-28, in a disposable group, on the Companion account and on the account's own labels), and `write list` says which (`verified`) and, for the rest, why not (`note`). `write list` also says what each touches: `private` (this account's own data), `visible` (other people see it) or `destructive` (it removes something that cannot be put back from here). ## Message database — `db` (6 commands)

The account's message database (`accounts/<ownId>/zalo.db`) is encrypted at rest (SQLCipher v4) and its key never leaves the machine's key provider, so `sqlite3`, `better-sqlite3`, DB Browser and bots can no longer open the file: these commands read it for them. They read the local database only (no login, unless the dkey layer needs one to open the key) and, but for `purge`, never go through a daemon: a reader beside a running `listen` / `mcp start` is what the database's write-ahead log is for, and each reads a consistent snapshot. CLI-only: raw SQL and a decrypted copy are an operator's or a bot's tools, not an MCP agent's (agents read through `zalo_get_history` / `zalo_search_messages`). **Hidden chats stay hidden until the PIN is given:** when the account has hidden conversations, `query` and `export` work on a snapshot with every row of those threads removed (messages with their search entries, reactions and row MACs, `threads`, `conv_state`, `board_items`, `reminders`, `cloud_items`, any table with a `threadId` column, and the `sync_state` keys named after them; the search index merged and the freed pages zeroed), so no SQL text reaches them, the search tables and `sqlite_master` included. The ids come from the list the listener and the hidden-chat commands keep on this machine; when none is known yet, one login reads it, and when that fails the command reads nothing (exit 1). `--include-hidden` asks for the hidden-chat PIN at a prompt that does not echo (or reads it from standard input with `--pin-stdin`; never an argument), checks it as `conv hidden` does (a login, Zalo's PIN hash, the same lockout: after 6 wrong PINs each try waits a growing back-off) and then includes them; a wrong PIN reads or writes nothing (exit 1), and with no terminal and no `--pin-stdin` it exits 2. `backup` keeps them: it is the account's restore image, encrypted under its key, that opens only through these commands, which leave them out again.

## Runtime policy — `policy` (4 commands)

The settings a running `listen` / `mcp start` takes **without a restart**: `confirmMode`, `hiddenChats`, `allowPinArgument`, `approval.*`, `media.*` delivery and links (not `media.downloadDir`), `webhook`, `webhookBatchSize`, `webhookMaxAge`, `quota.*`, `retention.*`, `presence.*` (on-demand presence; `presence.alwaysOn.*` in a tenant's or user's policy). One sealed file per account (`<accountDir>/policy.json`), per user (`<configDir>/users/<userId>.json`: its one tenant, the accounts it owns, its policy) and per tenant (`<configDir>/tenants/<tenantId>.json`, for its users' accounts and the accounts its legacy `quota.tenant.accounts` lists), each with a revision (`rev`). An account has one owning user and one tenant: a write that breaks that exits 1 (`MEMBERSHIP`). Layers, lowest first: built-in defaults, files (`mcp-config.json`, `storage.json`), the environment, then the policy (a tenant's, then the owning user's, then the account's own). Over an always-on cap (`presence.alwaysOn.maxPerUser`, default 1; `maxPerTenant`), the oldest always-on account is set to `on-demand` and the reply lists it in `demoted`; the resolvers read it on every call. A key read only at start (`httpPort`, `host`, `publicUrl`, `tls`, `oauth`, `trustedProxies`, `admin`, the key provider) or a secret (`webhookSecret`) is refused as `restartRequired`; an unknown key or a bad value is refused naming the key. A change goes through the account's running daemon (its loopback channel), which applies it at once (a `media.linkAuth` / `media.capability` change revokes the outstanding media links; a `webhook*` change moves the delivery); with no daemon it is written to the file for the next start. Every change and refusal is a line in `<configDir>/policy-audit.log` (who, which file, which keys, old and new rev; never a value). The same policy is served to a console by the MCP HTTP server's admin API (`/zalo/admin/policy`, `/zalo/admin/usage`; docs/configuration.md). Local only: no login. CLI-only: an agent never reads or changes its own policy.

| Command | Description |
|---------|-------------|
| `get [key] [--tenant <id>\|--user <id>] [--effective]` | The active (or `--account`) account's policy, or a tenant's, or a user's (with its `tenant` and `accounts`), with its `rev`, `updatedAt` and `updatedBy`; with a dotted key (`media.linkAuth`), that value only. `--effective`: the account's policy with its tenants' and owning user's merged in, as the resolvers read it. `--json`: `{target, rev, updatedAt, updatedBy, tenants?, owner?, tenant?, accounts?, policy}` or `{…, key, value}`. |

With `--user`, the keys `tenant` (`<tenantId>`) and `accounts` (`<ownId,ownId>`, replaces the list) set the user's membership. Exit 1 on a refused key or value. `--json`: `{target, rev, oldRev, changed, policy, demoted, notes?, via: "daemon"\|"file"}`. `notes` says what a change means beyond its value: `groups.onLeave` `keep` -> `purge` purges the groups kept so far on the next purge pass; `purge` -> `keep` changes later exits only (purged history never comes back). |

## Listener — `listen` (1 command)

A login Zalo keeps refusing (three refused logins in a row; for example after a QR login into Zalo in a browser elsewhere, since Zalo keeps one web login per account) leaves the daemon up **signed out** (below); exit **code 4** only with `ZALO_EXIT_ON_SIGNED_OUT=1`. A service manager should not restart on 3 or 4 (the shipped systemd unit has `RestartPreventExitStatus=3 4`). A new login is made only when Zalo refused the session or no usable socket came up after 8 tries, and while Zalo is in maintenance the daemon waits instead of retrying; `--status` shows `kicked`, `maintenance` and `relogin` as socket states, and a warning from 14 days before the saved login ends (`session` in the health snapshot, `zalo_session_days_left` in the metrics): a new QR login is then due. `-d, --daemon` spawns the listener as a detached background process (`windowsHide: true`, `.unref()`), redirects stdout and stderr to `~/.zalo-agent-cli/accounts/<ownId>/daemon.log` (through a level filter, an ISO timestamp per line and size rotation: `--log-level error|warn|info|debug`, default `info`, where `debug` adds the per-request and per-message lines, which carry caller addresses and message text; `ZALO_LOG_LEVEL[_<ownId>]`; `ZALO_LOG_FORMAT=json` for one JSON object per line; `ZALO_LOG_MAX_SIZE` default `50m` and `ZALO_LOG_KEEP` default `3` rotate it to `daemon.log.1`…; in the foreground only stderr is filtered, and only when a level or format is asked for), waits until its loopback channel (`daemon-channel.json`) is up, and returns the terminal prompt immediately; `--status` reports whether a background daemon (`listen` or `mcp start`) is running for the account (`pid`, `channelPort`, `logPath`) and, for a daemon new enough to answer `POST /status` on its loopback channel, its health: the socket (state, how long, reconnects, last close code), the age of the last event and message, pending coverage gaps, a running sync stage, the webhook outbox backlog, memory and event-loop delay, and a `WARNING:` line for anything that needs attention (`--json` adds the whole snapshot as `health`); `--stop` cleanly stops it over `POST /stop` on the loopback channel (running the exact same graceful shutdown handler as `SIGINT`: stamping `lastConnectedAt`, flushing delivered receipts, releasing `daemon.lock` and `daemon-channel.json`, with fallback to process kill). `--account <id>` (or global `--account <id>` / `ZALO_ACCOUNT`) pins this daemon to an exact registered numeric account ID across reconnects without changing the global active account in `accounts.json`. `-e/--events` is a comma-separated subset of `message,friend,group,reaction,read` (**default is `message,friend,group,reaction,read` — all five event types**), plus nine opt-in types that are never in the default: `typing` (someone is typing in a thread, or sending a file: prints `typing` events with the `uid` and `action` `"typing"` or `"fsending"`; The engine already uses the same frame to complete a send that is waiting for its file URL, so this only adds a line to the output; it is not needed to send files. Observed live: a `msg send-file` of a small text file, routed through a running `listen -d --events upload`, produced `{"event":"upload_attachment","fileId":…,"fileUrl":"https://…"}` in the daemon log). Neither is stored. The other three report a change made on another device, carried by a cmd 601 control, with the control's own data passed through whole as `control` (only key names of these controls have been seen live, so no other field is promised): `catalog` prints `catalog_changed` (a product or catalog added, edited or deleted: `act`, `catalogId`, `productIds`; nothing is cached, the `catalog` commands read live); `reminder` prints `reminder_created` and `reminder_updated` (a DM reminder made or edited on another device: `threadId`, `reminderId`, `by`, `title`, `emoji`, `startTime`, `stored`; the row is written as `sync-boards` would write it, whatever `--events` says, in `mcp start` too; the control's field names are not yet checked against a live value) and `reminder_removed` (a DM reminder deleted: `threadId`, `reminderId`, `removedBy`, `title`, `emoji`, `stored` says whether a cached row was removed; the row `sync-boards` stored is removed whatever `--events` says, in `mcp start` too); `devices` prints `devices_changed` (the account's linked-device list changed: `companions` is the count when the list is readable; the signed identity material `encIdentity`/`encAccSign` is removed from `control`; a line is logged to stderr every time, with or without the event, in `mcp start` too); `conversation` prints `mute_changed` (a conversation muted or unmuted: `threadId`, `threadType`, `muted`, `duration` in seconds, -1 until unmuted, `until`; the last control per conversation in a frame wins and a mute that has already run out is dropped), `archived_changed` (moved to Other or back: `archived`, `threads`, `version`), `auto_delete_changed` (`threadId`, `threadType`, `ttl` in ms, 0 off, `by`) and `labels_changed` (no fields; `label list` reads them); `quick-message` prints `quick_messages_changed` (`act` `create`/`update`/`delete`, `quickMessageIds`, `version`). Tracks connection gaps: after a reconnect, and on startup for the time since the last known-connected moment (anything of a second or more), the window is filed in `sync_gaps`. **Then it self-heals on every connect:** it asks Zalo's offline message queues (`510_1` for 1-1, `511_1` for groups) on its own socket for everything after the newest message it stored, pages until the server says there is no more, and writes what comes back insert-if-absent (`raw_data.src: "offline"`, printed as `[catch-up]`). No phone tap is involved, and live traffic keeps arriving and being stored meanwhile. A gap is resolved only for the window that pull actually covered. Coverage never starts before this device id's login (`deviceSince` in the saved credentials, or Zalo's `first_time_login_device`, the later): Zalo keeps the queue per device, so after a login with a new device id the window before it stays pending as `new-device`, however empty the queue's answer, unless a phone-backed restore finished after the login and reached back past it. A queue the server reports as dropped (`evict`) or reset is recorded as a gap of its own and announced as a **`queue_overflow`** event (`{event, accountId, fromTs, toTs, queues, direct, groups, pending, command}`, ids and counts only; on the output, JSONL and webhook here, and in `mcp start`'s log, webhook and MCP buffer); for the group queue the cloud message store of the groups the account is in is read back to the loss without a tap (most recently active first, at most 50 groups and 200 messages each, insert-if-absent, `raw_data.src: "group-cloud"`), and the group gap is closed when every group was reached; a 1-1 loss stays pending. A drain of 0 rows with no `evict` is a quiet queue, not an overflow. That run is the phone-backed `transfer-sync-v2`, which the daemon never starts on its own: it needs a tap on "ĐỒNG BỘ NGAY". Measured live 2026-09-30: a 75-minute outage came back in full from both queues with no prompt on the phone; under `--no-self-heal` a message sent during a drop stayed missing, and the next self-heal run recovered it and closed the gap the opt-out run had left pending. The cursor is the newest *stored* message, so a live message stored during a `--no-self-heal` run moves it past anything not yet recovered — that part stays pending for `sync` rather than being claimed. `--no-self-heal` records and reports gaps without the catch-up. | Command | Description |

| `sync-reactions [-w, --wait <seconds>] [-p, --pages <n>] [--no-removals]` | Retrieve existing reactions from Zalo's servers into `zalo.db`. ## On-demand presence — `presence` (4 commands)

The socket of the active (or `--account`) account's running daemon under on-demand presence (`presence.*` in the policy, `mcp-config.json` or `ZALO_PRESENCE_MODE`; docs/configuration.md). Each command goes to the daemon over its loopback channel (`POST /presence`); the CLI never opens a socket itself. A daemon that does not run on-demand presence keeps its socket connected: `status` says so (`onDemand: false`, from its health) and `wake` / `park` / `resume` exit 1. No daemon: `status` says `running: false`, `wake` / `park` / `resume` exit 1. `status`, `wake` and `park` are CLI-only; `resume` is also `zalo_profile` `presence_resume` over MCP.

| Command | Description |
|---------|-------------|
| `status` | `mode` (`on-demand`/`always-on`), `state` (`parked`, `waking`, `connected`, `parking`, `yielded`, `signed-out`; the last two print what to do), open `holds` by kind (counts only), `idleAt` (when it parks next), `wakesLastHour`, `lastWakeMs`, `lastCatchUpMs` and the metered `connectedMs` / `waitHeldMs`. `--json`: `{accountId, running, onDemand, mode, state, holds, ...}`. |
| `wake` | Open the socket now (a manual hold for `presence.minConnected`; it parks again after the idle timeout). Refused while yielded (`YIELDED`: use `resume`) or signed out (`SIGNED_OUT`: add the account again by QR); exit 1. |
| `park` | Close the socket now: not sooner than `presence.minConnected` after it connected, nor while a hold is open (then exit 1 with the reason). |
| `resume [-y, --yes] [--dry-run]` | Take the account back after a **yield** (on-demand: another session of this login took the socket, close 3000, and the daemon has refused every request with `YIELDED` since). Close the other session first. **Guarded**: without `--yes` nothing is asked of the daemon (exit 2); `--dry-run` says what it would do. Not yielded: exit 1 (`NOT_YIELDED`); signed out: exit 1 (`SIGNED_OUT`). Also `POST /zalo/admin/presence/resume` (admin API), the fleet controller's `POST /zalo/admin/accounts/<ownId>/presence/resume`, and `zalo_profile` `presence_resume`. `--json`: `{accountId, resumed, mode, state, ...}`. |

**Every personal command has an MCP action** (`tests/unit/mcp-cli-parity.test.js` holds the map). **CLI-only:** `oa …` and `zbs …` (separate, official APIs), `login`, `logout`, `status`, `account list|login|switch|remove|info|export`, `account security …` (an operator's steps on this machine's keys), `listen`, `mcp start`, `mcp webhook …`, `fleet …`, `update`, `profile lost-focus`, and `cloud get` (it takes the account's cloud key, which never passes through an agent or a tool input).

**Guarded tool actions.** `zalo_undo`, `zalo_delete_message`, `zalo_group` `leave`/`remove_member`/`remove_admin`/`transfer_owner`/`block_member`/`disperse`/`disable_link` (and `settings` turning `joinAppr` off), `zalo_friend` `reject`/`undo`/`remove`/`block`, `zalo_conversation` `unhide`/`hidden_pin_reset`/`delete`/`forget`, `zalo_reminder` `remove`, `zalo_poll` `lock`, `zalo_label` `update` (only when the new list leaves a label out), `zalo_catalog` `delete`/`delete_product`, `zalo_bank` `remove`, `zalo_auto_reply` `delete`, `zalo_quick_message` `remove`, `zalo_profile` `delete_avatar`, `zalo_cloud` `apply` and `zalo_write` take **`confirm`** and **`dryRun`**; `dryRun` on any other action is refused, and nothing is done. `dryRun: true` returns `{dryRun: true, sent: false, action, wouldDo, target, irreversible}` and sends nothing. What `confirm` means is the deployment's **confirm mode** (`confirmMode` in `mcp-config.json`, or `ZALO_MCP_CONFIRM_MODE[_<ownId>]`, which wins): **`agent`** (default) — the call needs `confirm: true`; without it the reply is an error whose first text is the CLI's JSON (`retryWith: {"confirm": true}`) and whose second is a line to read. **`human`** — the server asks the user itself through MCP elicitation (`elicitation/create`, a yes/no form saying exactly what will happen); only the user's accept-and-yes acts, and the caller's `confirm: true` does not stand in for it; a client that declared only URL-mode elicitation is sent a one-time approve page and the call waits for it; a client with no elicitation, and every call over the stateless HTTP transport (a fresh server per request cannot hear an answer), gets an error reply with `confirmationRequired: true`, `secureUrl` (the page, `/zalo/secure/<token>` on the server's port or under `publicUrl`), `ticketExpiresAt` (5 minutes) and `retryWith: {ticket}`: once the user approved there, the same call with `ticket` goes ahead, once (a ticket is bound to the account, the action and its target). Every guarded tool takes `ticket`. The approve page can ask for an **approver secret** (`approval.secret`: `password` set with `mcp approver set`, `pin` the hidden-chat PIN, `none`, or `auto`, the default: the password when one is set and the link reaches the agent); the reply says `approverSecret: true|false`. With **`approval.deliver: "webhook"`** the link is POSTed to the MCP webhook as `{event: "approval_requested", accountId, kind, action, wouldDo, target, secureUrl, expiresAt, approverSecret}` (signed like every webhook event) and the reply carries no link, only `confirmationRequired`, `approvalPending: true`, `ticket` (a claim token, not the page's), `ticketExpiresAt` and `deliveredTo: "webhook"`; `both` does both; PIN pages follow the same key. Under URL-mode elicitation the link goes only through the client's prompt and is never in the reply. **`off`** — no question (`dryRun` still works). `zalo_write` runs raw endpoints and stays guarded even when the mode is `off`. The deprecated `groupConfirm: false` and `ZALO_MCP_GROUP_CONFIRM=0` still mean `off` (`1` means `agent`); an explicit confirm mode wins over them. The server's instructions tell an agent to ask the user, the first time it meets a guarded action, how they want these handled, and to remember the answer.

See [MCP sync](../../docs/mcp-sync.md) / [Tiếng Việt](../../docs/mcp-sync.vi.md) for examples, retention and release prerequisites. Only the owner's explicit request authorizes `zalo_sync`; coverage reads never start it. Bulk media, boards, cloud and conversation-state sync remain CLI-only.

## Official Account — `oa`, ZBS — `zbs` and Social API — `social` (official APIs, 94 commands: 70 `oa` + 18 `zbs` + 6 `social`)

Completely independent from the personal (unofficial-API) account: separate OAuth credentials, separate storage (`~/.zalo-agent/oa-credentials.json`, note: **no `-cli` suffix** — different directory from personal `~/.zalo-agent-cli/`), no unofficial-API disclaimer shown. `zbs` uses the same OA token and credentials as `oa`. Multi-OA supported everywhere via `--oa-id <id>` (default: `"default"`); every command below takes it. The access token goes in the `access_token` header; an expired token (`-216`/`-220`, ZBS `-124`) is refreshed once under a file lock and the call retried once. A Zalo error prints `OA API error <code>: <Zalo's message> (<meaning from Zalo's error table>). <What to do>` and exits 1; a non-2xx or non-JSON answer is `http_<status>`. Webhook events, the error table, ZBS permissions and examples: [`oa-command-reference.md`](oa-command-reference.md).

**Guarded** (`-y, --yes` to act — without it nothing is sent, exit 2; `--dry-run` to preview): `follower delete-info`, `userfield delete`, `tag remove`, `purchase confirm-order`, `call consent-request` (each request is charged), `article remove`, `group remove-members`, `group delete`. A JSON argument or option (`--data`, `<json>`, an article, a template, `template_data`) is inline JSON (starting with `{` or `[`), `@file`, or the path of a JSON file.

**Removed in 3.0.0:** `oa store …` (Zalo Shop is not in Zalo's current OA docs), `oa menu` (no documented API), `oa msg list` (the list template exists only on the shut-down v2 message API), `oa msg status` (→ `zbs status`), and `-m, --msg-type transaction|promotion` (Zalo stopped them on the OA API on 01/03/2026 → `zbs send` / `zbs uid`).

### Webhook Listener — `oa listen`

| Command | Description |
|---------|-------------|
| `listen [-p, --port <port>] [-s, --secret <key>] [--no-verify] [-e, --events <list>] [--path <path>] [--app-id <id>] [--verify-file <path>] [--verify-meta <tag>]` | Start a local HTTP webhook server for OA and ZBS events. `-p/--port` default 3000. `-s/--secret` (the OA Secret Key from the app's Webhook settings) checks each event's `X-ZEvent-Signature` as Zalo's docs define it: `sha256(app_id + body + timestamp + OA secret key)` in hex — a plain SHA-256 over the concatenation, not an HMAC — compared in constant time; a bad or missing signature gets 401. Three documented events carry no `app_id` in their body (`extension_purchased`, `change_template_quality`, `change_oa_daily_quota`): for them the app id from `--app-id`, or else the one `oa setup`/`oa init` saved, is used. A warning is printed if no secret is given; `--no-verify` disables the check even with a secret set. `-e/--events` filters to a comma-separated subset (default `all`) of the 79 events Zalo's OA and ZBS docs give (listed in `oa-command-reference.md`, source `OA_WEBHOOK_EVENTS` in `src/commands/oa-listen.js`); a name Zalo does not document prints a warning at start. `follow`/`unfollow` name the user by `follower.id`. The listener **answers 200 as soon as an event is accepted**, before printing it — Zalo wants it within 2 seconds, redelivers, and eventually disables the webhook — and a redelivery (Zalo's `num_retry` header) is flagged as such, `_num_retry` in `--json`. `--path` changes the webhook URL path (default `/webhook`). Domain verification serves what Zalo gives, never a made-up page: `--verify-file <path>` serves the HTML file downloaded from the app's "Xác thực domain" page, unchanged, at its own name (under any path, for URL-prefix verification); `--verify-meta '<meta …>'` puts the tag Zalo shows in the head of `/` (and of any path ending in `/`). The DNS TXT method needs neither. A GET with `hub.challenge` is echoed back — this listener's own convenience for tools that probe webhooks that way, not part of Zalo's webhook. Body size capped at 1 MB. |

### Social API — `social`

A Zalo user logs in to **your app** and the app reads that user's app-scoped ID, name and avatar (Zalo's Social API: OAuth v4 with PKCE and `state`, then `graph.zalo.me`). Independent from the personal account and from the OA: its own app login per `--profile` (default `default`) in `~/.zalo-agent/social-credentials.json` (0600). The app's callback URL (developers.zalo.me → the app → Đăng nhập → Web) must be `http://localhost:<port>/callback` or `<callback-host>/callback`. Every call carries `appsecret_proof`. The access token lasts 1 hour and renews itself (once, on error 452, serialized); the login lasts at most 30 days, because a refreshed token keeps what was left of the one it replaced. A Zalo error prints `Social API error <code>: <message> (<meaning from the Social docs' table>)`; `-501` means the call came from an IP outside Vietnam. Not an MCP tool.

| Command | Description |
|---------|-------------|
| `setup --app-id <id> --secret <key> [--profile <name>]` | Save the app's ID and secret key. |
| `login [--app-id <id>] [--secret <key>] [-p, --port <port>] [--callback-host <host>] [--dpop] [--profile <name>]` | Open Zalo's permission page (`oauth.zaloapp.com/v4/permission`, PKCE and `state`), wait for the callback on 127.0.0.1 (0.0.0.0 with `--callback-host`), check `state`, exchange the code with the verifier, save the tokens, then show the user. Port default 3457. `--dpop` binds the tokens to a new P-256 key pair (DPoP, ES256): every later call and refresh carries a proof signed with it, so a stolen token is useless on its own. |
| `refresh [--profile <name>]` | Renew the access token now (the refresh token is single use; serialized under a lock). Refused, with nothing sent, once the 30-day login ended. |
| `me [--fields <list>] [--picture small\|normal\|large] [--profile <name>]` | `GET graph.zalo.me/v2.0/me`: `id` (this app's ID for the user, not usable by other apps), `name`, `picture` (smallest unless `--picture`), and `is_sensitive` when asked (a user the law requires special handling for). Other fields are refused before any request. |
| `status [--profile <name>]` | Whether a user is logged in, when the access token and the login end, DPoP on or off. Never shows a token. |
| `logout [--profile <name>]` | Forget the user's tokens and DPoP key on this machine; the app's ID and secret stay. |
