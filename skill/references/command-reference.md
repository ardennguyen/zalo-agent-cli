# zalo-agent CLI — Full Command Reference

Exhaustive reference for every command, subcommand, and flag `zalo-agent` exposes. Generated by reading every file in `src/commands/` and `src/mcp/mcp-tools.js` directly (not from prior docs), current as of v2.0.0.

## Global Behavior

- **`--json`** (global flag, works before any command) — machine-readable JSON output for every command. Also suppresses the startup disclaimer and the "Note:"/`info()` lines that would otherwise print to stdout.
- **`-V, --version`** — print the installed version.
- **`-h, --help`** — help for the CLI or any subcommand (`zalo-agent <group> --help`).
- **Disclaimer**: on every command *except* `oa` commands and JSON mode, the CLI prints: "This tool uses unofficial Zalo APIs (zca-js) — your account may be banned. Use at your own risk." (VN translation included). `oa` commands are exempt because they use the official Zalo OA REST API.
- **Auto-login**: before running any command, the CLI auto-logs-in the active account — *except* for `login`, `account`, `help`, `version`, `update`, `oa`, and `mcp` (these manage their own auth or don't need one).
- **Update check**: a non-blocking background check against the npm registry runs before every command except `update` itself. It is silently skipped when stdout is not a TTY (piped/scripted use), in `--json` mode, or when the env var `ZALO_AGENT_NO_UPDATE_CHECK` is set. It only ever warns when a genuinely *newer* semver version is published — a local dev build ahead of npm (e.g. `2.0.0-dev` vs published `1.0.7`) will not trigger a false "update available"/downgrade warning.
- **Thread type flag** (`-t, --type <n>`), used across almost every messaging/thread command: `0` = User/DM (default), `1` = Group.

## Top-Level (Auth & Maintenance)

| Command | Description |
|---------|-------------|
| `login [-p, --proxy <url>] [-n, --name <label>] [--qr-url] [-q, --qr-port <port>] [--credentials <path>]` | Login via QR scan, or from an exported credentials file (`--credentials`, skips QR entirely). A local HTTP server for viewing the QR in a browser always starts (default port 18927, override with `--qr-port`); `--qr-url` is accepted but the server starts regardless — useful to remember for VPS/headless use. During the QR flow the CLI now surfaces every zca-js QR event: generated (shows QR + starts HTTP server), **scanned** (prints who scanned it — name + avatar URL — and prompts to confirm on phone), **declined** (login fails immediately, does not hang until the 60s timeout), and **expired** (auto-retries with a fresh QR, since zca-js itself doesn't). |
| `logout [--purge] [--delete-history] [--no-remote]` | Logout, mirroring Zalo Web's own logout dialog. By default also invalidates the session **server-side** (a real `logoutV2()` call — confirmed live, a follow-up authenticated request afterward fails with error 600) unless `--no-remote` is passed (old local-only behavior: just forgets the in-memory session, credentials/cookie stay valid indefinitely). `--delete-history` additionally deletes the local chat cache (`zalo.db` + downloaded media) for the account, matching Zalo Web's "Delete chat history on logout" checkbox. `--purge` fully removes the account from this machine: wipes the *entire* per-account data directory (db, media, sync keys, daemon.lock — same as `account remove`), deletes the saved credentials, and removes the account from the registry (implies everything `--delete-history` does and then some). `--purge` refuses (aborts, leaving credentials/registry untouched) if a `listen` daemon still holds the account's lock. |
| `status` | Show current login state: logged in y/n, own user ID, active account name/proxy. |
| `whoami` | Show current user's full Zalo profile (fetched live). |
| `update` | Self-update: runs `npm install -g @ardennguyen/zalo-agent-cli@latest`. |
| `sync-mobile [-t, --transfer] [-F, --force] [-d, --days <n>] [--from <date>] [-L, --legacy] [-M, --messages-only] [-w, --wait <seconds>]` | Restore message history from the phone into the local cache (`zalo.db`). **`-t/--transfer` is the real, phone-backed restore (transfer-sync-v2, socket cmd 590/591).** It sends ONE sync request the owner confirms on their phone (tap "ĐỒNG BỘ NGAY"), enumerates every conversation (conversation round), then requests message history in shards of ≤30 partitions (server cap), decrypts each batch with Zalo's `libzproto` WASM (fetched+cached from Zalo's CDN on first run), Zstd-decompresses, protobuf-decodes, maps each opaque conversation id to the real numeric threadId + name via the friend/group lists (both expose `globalId`), and writes messages through the same `insertMessage()`/`upsertThread()` the listener uses. One phone tap covers the whole run (message shards inherit the conversation-round confirmation). Non-friend 1-1 / OA conversations may stay keyed by their opaque id (no local name/id mapping without the `/api/gid/decrypt` fallback). **Default path (no flag):** a best-effort server socket backfill (cmd 510/511) that usually returns empty — kept as a cheap probe; the real data path is `--transfer`. All paths take `daemon.lock` (refuse while a `listen` daemon runs) and obey Zalo's one-web-session rule. `-w/--wait` bounds each phase (default 30s; `--transfer` floors it at 180s for the phone confirmation). **`-L, --legacy`** tries the retired `pull_mobile_msg`/`get_crossdb` endpoint — one attempt, pings the phone, recovers nothing. `-F/--force` skips the "already synced recently" debounce (which otherwise avoids re-pinging the phone). **`-d, --days <n>`** restores only the last *n* days (whole number ≥ 1) instead of full history. It sets the `from` bound on **both** the conversation round and the message rounds, so a short window returns fewer conversations, sends fewer ≤30-partition shards, and finishes far sooner — it is not just a per-conversation cut. **Default: full history, with no lower bound at all** — the `from` field of the cmd 590 query is sent as 0, so the phone is asked for everything it still holds. This was previously pinned at 2024-01-01, which silently meant an account with 2018 messages never had them requested and nothing in the output said so. **`--from <YYYY-MM-DD>`** sets an explicit lower bound and overrides `--days`; a date in the future, before Zalo existed, or unparseable falls back to full history rather than to a silently narrow window. Both are rejected with exit 1 without `--transfer`. Rejected with exit 1 when passed without `--transfer`, since no other path sends that query. The freshness debounce is window-aware: each successful transfer records how far back it reached (`lastSyncOkFrom`), so a narrow run does not suppress a wider one (`--days 7` then a full sync ten minutes later still runs; the reverse is still skipped). Messages are stored with their real type: the payload's numeric `msgType` plus the attachment shape decide the row (`text`, `photo`, `video`, `file`, `gif`, `sticker`, `link`, `card`, `event`, `group_event`, `poll_event`, `profile_card`, `deleted`, or `type_<n>` for a type this build has not seen), and the whole `meta` block — attachments, quote, mentions, TTL, bubble styling — is kept in `raw_data` as JSON alongside `cliMsgId`, so a synced row can anchor a reply the same way a listener-captured row can. The cmd 590 stream carries media *links*, never bytes, so once the messages are stored a `--transfer` run **downloads its attachments automatically** — a restored conversation whose photos are missing is only half restored. That fetch happens after the socket is closed and `daemon.lock` released (it needs neither), it is uncapped, and interrupting it is safe because `sync-media` resumes from whatever still has no `localPath`. A media failure never fails the run; the messages are already stored. **`-M, --messages-only`** skips the fetch for a fast history-only restore, and is rejected with exit 1 without `--transfer`. `has_attachment` marks rows carrying a fetchable file, and `sync-media` runs the same fetch on its own with filters. **Links are a media kind too** — Zalo's own media store has three tabs (image/video, file, link) — so a shared link is classified `link` and kept with its url/title/description/thumbnail, queryable via `getLinkMessages()`. It is deliberately kept out of the download queue (a link has no bytes) and kept distinct from OA notification cards and profile cards, which also carry an href; Zalo Web is equally narrow, indexing only `action: "recommened.link"`. A bare URL typed inside a plain-text message is not indexed as a link — Zalo Web does not index those either. The conversation round's own fields (`respondedByMe`, `lastGlobalId`, `lastClientId`) land on the `threads` row; a later listener write never clears them. |
| `sync-media [-T, --thread <id>] [-k, --kind <kinds>] [-n, --limit <n>] [-d, --days <n>] [-c, --concurrency <n>] [-m, --max-size <mb>] [--thumbs] [--dry-run]` | Download the attachments a mobile sync recorded. transfer-sync carries only CDN references, so this is the fetch step — and it needs **no phone confirmation and no socket**, so it can run while `listen` holds the account. Reads rows with `has_attachment = 1` and no `localPath`, writes to `accounts/<ownId>/media/<threadName>/<date>_<time>_<msgId>_<name>.<ext>`, and records `localPath` back on the message. A Zalo CDN link that has aged out answers **HTTP 200 with a JSON error body** (`{"err_code":"1"}`) rather than failing, so the body is inspected; a lapsed link is retried once through `/api/message/renewlink` (cmd 12094), which only works while Zalo still holds the file. `--kind` filters to `photo,video,file,gif,voice,audio,doodle` (default: all). `--dry-run` reports the plan without touching the network. A row that already has a `localPath` is never re-fetched. By default the run is limited to the window the **last mobile sync actually covered** (`lastSyncOkFrom`), since media outside it was never refreshed and its links are the likeliest to be dead — **`--all-history`** considers everything, and an explicit `--days` still wins. **`--prune <days>`** switches the command to cleanup: it deletes downloaded media attached to messages older than N days and **never touches message text**. A prune is recorded as a decision (`mediaPrunedAt`), not just a cleared `localPath` — otherwise the next `sync-mobile --transfer`, which fetches media by default, would re-download exactly what was deliberately deleted. Automatic fetches skip pruned media; **`--include-pruned`** deliberately brings it back, and downloading a file again clears the marker. **`--prune all`** (or `--prune <n> --all`) deletes every downloaded file regardless of age — a named mode rather than a very large cutoff, so no arithmetic slip on a date can become delete-everything. `--prune 0`, a negative, or anything non-numeric is rejected with a clear message before the account is even loaded. Always preview with `--dry-run`. **Deleting a conversation does not clean up after itself**: `conv delete` and `group disperse` call Zalo's API only — the local `messages`, `threads`, `board_items`, `reminders` and `reactions` rows all remain and their downloaded media stays on disk, never refreshed by a later sync because the conversation no longer appears in the conversation round. **`--prune-orphans`** reclaims the media of every such conversation in one pass (message text kept). Orphans are found two ways: a `leave`/`remove_member`/`block_member` event about **you** flags the thread (`threads.leftAt`) as it happens, and a transfer sync compares its conversation round against the cache and reports anything missing. `conv delete` and `group disperse` now flag the thread locally too. To remove the history as well, `conv forget <threadId>` or `conv forget --orphans` deletes the messages, reactions, board items, reminders, cloud index and media for those conversations — local only, Zalo is never contacted — and both support `--dry-run`. **`--timeout <seconds>`** (default 60) bounds a single download — `fetch()` has none of its own, and a server that sends headers then stops writing would otherwise block a worker indefinitely. |
| `sync-boards [-T, --thread <id>] [-n, --limit <n>] [-c, --concurrency <n>] [--no-reminders] [--no-boards]` | Sync notes ("Ghi chú"), pinned messages, polls and reminders ("Nhắc hẹn") into `board_items` / `reminders`. **None of this is in the message stream** — Zalo keeps it behind per-thread board endpoints (`/api/board/list` for groups, `/api/board/listReminder` and `/api/board/oneone/list` for reminders), so it needs its own pass. The conversation *events* announcing them do arrive as messages (`msgType` 24 for reminders, 26 for polls), but the objects themselves only exist here. One request per thread, so it runs at low concurrency with a pause between calls and defaults to the 200 most recent threads. Groups have boards; 1-1 conversations get reminders only. Needs no phone confirmation. |
| `sync-cloud [-p, --pages <n>] [-s, --page-size <n>] [-r, --resume <noiseId>]` | Walk the zCloud ("Cloud của tôi") media index into `cloud_items` — the reconciliation Zalo Web runs when the socket delivers a cmd 621 `mycloudMedia` event. Pages `/cloudmedia/queue/pc/verify` by `lastNoiseId` (Zalo Web uses 300/page and throttles to once per 30 min) and records each item's `cloudUrl`, `encryptKey`, checksum and size. **It records where backups live; it does not download or decrypt them** — each blob is E2EE under a per-item key plus the account's cloud viewer key, and that scheme is not implemented. Endpoints are reconstructed from Zalo Web's bundle and have not been verified against a live account. Needs no phone confirmation. |

**Env vars:** `ZALO_AGENT_NO_UPDATE_CHECK` (any value) disables the background update-version check entirely.

## Accounts — `account` (7 commands)

Multi-account management, each account bound 1:1 to its own dedicated proxy.

| Command | Description |
|---------|-------------|
| `list` | List all registered accounts (proxy always masked in output). |
| `login [-p, --proxy <url>] [-n, --name <label>] [--qr-url]` | Add a new account via QR (same underlying flow as top-level `login`, registered separately for the multi-account UX). |
| `switch <ownerId>` | Switch the active account (accepts a partial ID/name match if unambiguous), restarting the connection with that account's own proxy. |

## Listener — `listen` (1 command, always running)

| Command | Description |
|---------|-------------|
| `listen [-e, --events <types>] [-f, --filter user\|group\|all] [-w, --webhook <url>] [--no-self] [--auto-accept] [--save <dir>]` | Unified real-time listener over one WebSocket, with auto-reconnect + auto-re-login. `-e/--events` is a comma-separated subset of `message,friend,group,reaction` (**default is `message,friend`, not all four** — `group` and `reaction` must be explicitly requested). `--events` selects what is **printed/forwarded**, not what is **stored**: reactions, recalls, delivery receipts, board changes and "you left this group" are written to `zalo.db` on every run, because none of them can be recovered afterwards (the mobile-sync payload has no reaction field at all). `-f/--filter` restricts message events to DMs (`user`), groups (`group`), or both (`all`, default). `--no-self` hides your own sent messages from the output only — they are still written to the cache (`selfListen` is enabled, so everything this account sends from any device, including the phone, is captured; previously all of it was dropped by the library before any handler ran). `--auto-accept` auto-accepts incoming friend requests. `--webhook <url>` POSTs every event as JSON (fire-and-forget, 5s timeout, never blocks event processing). `--save <dir>` appends every event to a per-thread JSONL file (`<dir>/<threadId>.jsonl`) — a practical workaround since the Zalo API itself only returns ~20 recent messages. Every incoming message also writes to the local SQLite cache (`zalo.db`) through `core/live-store.js` — the same writer a running mobile sync uses — and triggers media auto-download through the same downloader `sync-media` uses, into the shared `accounts/<ownId>/media/<conversation>/` layout. Both kinds of Zalo removal are applied to the message they name instead of being stored as new rows: a recall-for-everyone (*Thu hồi*) arrives as the `undo` event and names its target in `content.globalMsgId`, while a delete-for-me (*Xoá ở phía tôi*) arrives as a `message` with `msgType: chat.delete` and names it in `content[0].globalDelMsgId` (falling back to `clientDelMsgId`). Both produce the same tombstone the phone keeps, record the kind in `raw_data.removedAs`, preserve `cliMsgId`, and take the downloaded media with them (`has_attachment` cleared, `mediaPrunedAt` set, file deleted). Rows are classified through the **same** vocabulary the mobile sync uses (`photo`, `file`, `text`, …, not zca-js's `chat.photo`/`share.file`), carry the same attachment shape, and set `has_attachment` — so one query reaches both capture paths and `sync-media` can fetch listener-captured media too. Requires an exclusive per-account lock (`daemon.lock`) — one live socket and one cache writer per account, shared with `mcp start`, which now takes the same lock. A live message never renames a conversation: `dName` is the *sender's* display name, a group has exactly one name that no message carries, and a deliberate 1-1 alias is never overwritten — naming comes from `sync-mobile --transfer`/`sync-boards` (via `getGroupInfo`) or the MCP thread index. Tracks connection gaps and attempts a backfill after a reconnect or on startup if the last known-connected time was more than ~30s ago. **That backfill currently calls the retired `pull_mobile_msg` path and therefore recovers nothing** — it reports `legacy-retired` and moves on. Pointing it at the socket backfill `sync-mobile` now uses is open work. |

## Reactions — `sync-reactions`

| Command | Description |
|---------|-------------|
| `sync-reactions [-w, --wait <seconds>] [-p, --pages <n>] [--no-removals]` | Retrieve existing reactions from Zalo's servers into `zalo.db`. Reactions are the one thing `sync-mobile --transfer` cannot restore — the Sync2 payload has no reaction field — but they **are** served over the socket on cmd 610 (1-1) and 611 (group), which is how Zalo Web shows them after a fresh login.
