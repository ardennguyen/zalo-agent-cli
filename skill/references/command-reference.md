# zalo-agent CLI — Full Command Reference

Exhaustive reference for every command, subcommand, and flag `zalo-agent` exposes. Generated by reading every file in `src/commands/` and `src/mcp/mcp-tools.js` directly (not from prior docs), current as of v2.0.0.

## Global Behavior

- **`--json`** (global flag, works before any command) — machine-readable JSON output for every command. Also suppresses the startup disclaimer and the "Note:"/`info()` lines that would otherwise print to stdout.
- **`-V, --version`** — print the installed version.
- **`-h, --help`** — help for the CLI or any subcommand (`zalo-agent <group> --help`).
- **Disclaimer**: on every command *except* `oa` commands and JSON mode, the CLI prints: "This tool uses unofficial Zalo APIs (zca-js) — your account may be banned. Use at your own risk." (VN translation included). `oa` commands are exempt because they use the official Zalo OA REST API.
- **Auto-login**: before running any command, the CLI auto-logs-in the active account — *except* for `login`, `account`, `help`, `version`, `update`, `oa`, and `mcp` (these manage their own auth or don't need one).
- **Update check**: a non-blocking background check against the npm registry runs before every command except `update` itself. It is silently skipped when stdout is not a TTY (piped/scripted use), in `--json` mode, or when the env var `ZALO_AGENT_NO_UPDATE_CHECK` is set. It only ever warns when a genuinely *newer* semver version is published — a local dev build ahead of npm (e.g. `2.0.0-dev` vs published `1.0.7`) will not trigger a false "update available"/downgrade warning.
- **Thread type flag** (`-t, --type <n>`), used across almost every messaging/thread command: `0` = User/DM (default), `1` = Group.

## Top-Level (Auth & Maintenance)

| Command | Description |
|---------|-------------|
| `login [-p, --proxy <url>] [-n, --name <label>] [--qr-url] [-q, --qr-port <port>] [--credentials <path>]` | Login via QR scan, or from an exported credentials file (`--credentials`, skips QR entirely). A local HTTP server for viewing the QR in a browser always starts (default port 18927, override with `--qr-port`); `--qr-url` is accepted but the server starts regardless — useful to remember for VPS/headless use. During the QR flow the CLI now surfaces every zca-js QR event: generated (shows QR + starts HTTP server), **scanned** (prints who scanned it — name + avatar URL — and prompts to confirm on phone), **declined** (login fails immediately, does not hang until the 60s timeout), and **expired** (auto-retries with a fresh QR, since zca-js itself doesn't). |
| `logout [--purge] [--delete-history] [--no-remote]` | Logout, mirroring Zalo Web's own logout dialog. By default also invalidates the session **server-side** (a real `logoutV2()` call — confirmed live, a follow-up authenticated request afterward fails with error 600) unless `--no-remote` is passed (old local-only behavior: just forgets the in-memory session, credentials/cookie stay valid indefinitely). `--delete-history` additionally deletes the local chat cache (`zalo.db` + downloaded media) for the account, matching Zalo Web's "Delete chat history on logout" checkbox. `--purge` fully removes the account from this machine: wipes the *entire* per-account data directory (db, media, sync keys, daemon.lock — same as `account remove`), deletes the saved credentials, and removes the account from the registry (implies everything `--delete-history` does and then some). `--purge` refuses (aborts, leaving credentials/registry untouched) if a `listen` daemon still holds the account's lock. |
| `status` | Show current login state: logged in y/n, own user ID, active account name/proxy. |
| `whoami` | Show current user's full Zalo profile (fetched live). |
| `update` | Self-update: runs `npm install -g @ardennguyen/zalo-agent-cli@latest`. |
| `sync-mobile [-F, --force] [-L, --legacy] [-w, --wait <seconds>]` | Backfill recent message history into the local cache (`zalo.db`). **Default path — no phone contact:** opens the WebSocket and asks the server for old messages (socket cmd 510 for DMs, 511 for groups), writing anything that arrives through the same `insertMessage()`/`upsertThread()` the listener uses. **Measured 2026-09-20: Zalo answers both commands with an empty set on the development account, even when given the exact `lastId` anchors Zalo Web sends — so this usually recovers nothing and says so.** The only sync path still carrying data is `transfer-sync-v2` (socket cmd 590/591, libsignal-encrypted), which is not implemented. See tests/NOTES.md § Mobile sync. Takes `daemon.lock`, so it refuses while a `listen` daemon is running, and Zalo's one-web-session rule means it will close a browser Zalo Web session on the same account. `-w/--wait` bounds the whole operation (default 30s). **`-L, --legacy`** instead tries the retired `pull_mobile_msg`/`get_crossdb` phone-transfer endpoint — **one attempt only**, and it does ping the mobile app. Zalo no longer serves that path (0 call sites in Zalo Web's own bundle), so it reports the dead end and points back at the default. `-F/--force` skips the local "already synced" debounce that mirrors Zalo Web's own gap check. |

**Env vars:** `ZALO_AGENT_NO_UPDATE_CHECK` (any value) disables the background update-version check entirely.

| `sticker <threadId> <keyword> [-t 0\|1]` | Search stickers by keyword and send the first match. |
| `sticker-list <keyword>` | Search stickers by keyword, returns a list of sticker IDs (no send). |
| `sticker-detail <stickerIds...>` | Get full details for one or more sticker IDs. |
| `sticker-category <categoryId>` | Get details for a sticker category. |
| `react <msgId> <threadId> <reaction> [-t 0\|1] [-c, --cli-msg-id <id>]` | React to a message. Reaction codes: `:>` (haha), `/-heart` (heart), `/-strong` (like), `:o` (wow), `:-((` (cry), `:-h` (angry) — plus `:-*` (kiss), `:')` (tears of joy), `/-weak` (dislike), `/-shit` (poop). **`-c/--cli-msg-id` is needed for the reaction to actually appear** — without it the API is called with `cliMsgId` defaulted to `msgId`, which often doesn't register visibly. Get the real cliMsgId from `listen --json` or `send --json` output. |

| `undo <msgId> <threadId> [-t 0\|1] -c, --cli-msg-id <id>` | Recall/undo a message for **both sides** (like the Zalo app's "Thu hồi"). `-c/--cli-msg-id` is a hard requirement — the command errors out immediately if omitted, no silent fallback. |
| `forward <msgId> <threadId> [-t 0\|1]` | Forward a message to another thread. |
| `history <threadId> [-t 0\|1] [-n, --limit <n>] [--scan <n>] [--from-msg-id <id>] [--timeout <ms>] [--no-cache]` | Fetch message history. **Groups**: tries the REST API first (`getGroupChatHistory`), falls back to the WebSocket global-stream scan if that fails. **DMs**: always uses the WebSocket scan (`requestOldMessages`, paginated via `--scan`/raw messages scanned per page, capped by `--timeout` per page wait). By default reads from the local SQLite cache (`zalo.db`) first and only falls back to a live fetch if the cache has fewer than `--limit` messages; **`--no-cache` forces a live fetch even when the cache already has enough**, and amends the DB with whatever it fetches. `--from-msg-id` anchors the WebSocket scan to start from an older message ID (pagination). Default `--limit` 50, `--scan` 2000, `--timeout` 15000ms. |

**Reaction codes reference:** `:>` Haha · `/-heart` Heart · `/-strong` Like · `:o` Wow · `:-((` Cry · `:-h` Angry · `:-*` Kiss · `:')` Tears of joy · `/-weak` Dislike · `/-shit` Poop

**Text style keys** (for `--style start:len:style`): `bold`/`b`, `italic`/`i`, `underline`/`u`, `strikethrough`/`s`, `red`, `orange`, `yellow`, `green`, `big` (large font), `small` (small font).

**Bank aliases** (for `send-bank`/`send-qr-transfer` `--bank`): ocb, vcb, vietcombank, bidv, mb, mbbank, techcombank, tpbank, acb, vpbank, msb, sacombank, hdbank, seabank, shb, eximbank, vib, agribank, vietinbank, ctg, scb, ncb, abbank, dongabank, kienlongbank, shinhan, hsbc, cimb, woori, and 25+ more (55+ total) — or pass a raw BIN code directly.

## Accounts — `account` (7 commands)

Multi-account management, each account bound 1:1 to its own dedicated proxy.

| Command | Description |
|---------|-------------|
| `list` | List all registered accounts (proxy always masked in output). |
| `login [-p, --proxy <url>] [-n, --name <label>] [--qr-url]` | Add a new account via QR (same underlying flow as top-level `login`, registered separately for the multi-account UX). |

| `remove <ownerId>` | **Fully remove an account from this machine**: if it's the currently active/logged-in one, invalidates its server-side session first (same `logoutV2()` call `logout` uses); then wipes its entire local data directory (`zalo.db` + WAL sidecars, `media/`, `sync/` RSA keys, `daemon.lock`); deletes its credentials file; drops it from the registry (activating the next remaining account, if any). | `devices` | List devices/sessions currently linked to the active account (read-only) — shows the master session ID, last-update time, and any other "companion" linked sessions. |

**Storage layout:** `~/.zalo-agent-cli/accounts.json` (registry) · `~/.zalo-agent-cli/credentials/cred_<ownId>.json` (0600) · `~/.zalo-agent-cli/accounts/<ownId>/{zalo.db, media/, sync/, daemon.lock}` (per-account cache/media/keys/lock) · `~/.zalo-agent-cli/qr.png` (last QR).

| `listen [-e, --events <types>] [-f, --filter user\|group\|all] [-w, --webhook <url>] [--no-self] [--auto-accept] [--save <dir>]` | Unified real-time listener over one WebSocket, with auto-reconnect + auto-re-login. `-e/--events` is a comma-separated subset of `message,friend,group,reaction` (**default is `message,friend`, not all four** — `group` and `reaction` must be explicitly requested). `-f/--filter` restricts message events to DMs (`user`), groups (`group`), or both (`all`, default). `--no-self` excludes your own sent messages. `--auto-accept` auto-accepts incoming friend requests. `--webhook <url>` POSTs every event as JSON (fire-and-forget, 5s timeout, never blocks event processing). `--save <dir>` appends every event to a per-thread JSONL file (`<dir>/<threadId>.jsonl`) — a practical workaround since the Zalo API itself only returns ~20 recent messages. Every incoming message also writes to the local SQLite cache (`zalo.db`) and triggers media auto-download. Requires an exclusive per-account lock (`daemon.lock`) — only one `listen` process per account at a time. Tracks connection gaps and attempts a backfill after a reconnect or on startup if the last known-connected time was more than ~30s ago. **That backfill currently calls the retired `pull_mobile_msg` path and therefore recovers nothing** — it reports `legacy-retired` and moves on. Pointing it at the socket backfill `sync-mobile` now uses is open work; see tests/NOTES.md § Mobile sync. |

## MCP Server — `mcp start` (AI agent integration)

| Command | Description |
|---------|-------------|
| `mcp start [--config <path>] [--http <port>] [--auth <token>] [--host <address>]` | Start the MCP server. **stdio transport** (default, for Claude Code/Cowork-style clients) if `--http` is omitted. **HTTP transport** if `--http <port>` is given — binds to `127.0.0.1` by default, override with `--host <address>` (e.g. `0.0.0.0` for remote/VPS access); `--auth <token>` requires `Authorization: Bearer <token>` on every endpoint except `/health`. `--config <path>` points to a custom config file (default `~/.zalo-agent-cli/mcp-config.json`). All console output is redirected to stderr in this mode (stdout is the JSON-RPC transport channel in stdio mode) — even library log noise from zca-js/chalk is caught. Auto-reconnects and re-logs-in on WebSocket close (except a duplicate-session close, which is fatal by design). Builds an in-memory `ThreadNameCache` (groups + friends) at startup for name enrichment and fuzzy search. Auto-downloads media (images/audio/video) for buffered messages in the background. Sends a batched Zalo-group notification when no MCP client is connected and `notify.enabled` is on in config (see below). |

## Official Account — `oa` (official REST API v3.0, ~32 commands)

Completely independent from the personal zca-js account: separate OAuth credentials, separate storage (`~/.zalo-agent/oa-credentials.json`, note: **no `-cli` suffix** — different directory from personal `~/.zalo-agent-cli/`), no unofficial-API disclaimer shown. Multi-OA supported everywhere via `--oa-id <id>` (default: `"default"`).

### Auth & Setup

| Command | Description |
|---------|-------------|
| `login --app-id <id> --secret <key> [-p, --port <port>] [--callback-host <host>] [--oa-id <id>]` | OAuth login: opens a browser to the Zalo consent screen and starts a local callback server (default port 3456) to receive the auth code. `--callback-host <url>` switches to VPS/headless mode: binds the callback server to `0.0.0.0` instead of `127.0.0.1`, skips auto-opening a browser (prints the URL to open manually on a local machine instead), and uses that host for the redirect URI. 2-minute timeout. |
| `refresh [--oa-id <id>]` | Refresh the access token using the stored refresh token. |
| `setup <access-token> [--oa-id <id>]` | Manually set an access token, bypassing OAuth entirely (e.g. copied from another machine). |
| `whoami [--oa-id <id>]` | Show the OA's profile: name, ID, description, follower count. |
| `init [--oa-id <id>] [--app-id <id>] [--secret <key>] [--tunnel ngrok\|cloudflared\|none] [--webhook-url <url>] [--verify-code <code>] [-p, --port <port>] [--skip-webhook] [--skip-login]` | **Guided setup wizard** — works both interactively (human, prompts at each step) and non-interactively (agent mode, triggered automatically whenever `--app-id` is passed). Walks through: (1) save app-id/secret, offering to reuse existing saved creds; (2) OAuth login (skippable with `--skip-login`, or auto-skipped in agent mode if a token is already saved) and profile verification; (3) an interactive-only prerequisite checklist (callback URL, API enablement, permissions at developers.zalo.me); (4) webhook exposure — `--skip-webhook` skips entirely; `--webhook-url` saves a pre-existing URL (VPS/n8n/etc., optionally with `--verify-code`); otherwise picks a tunnel type (interactively prompted 1-5, or `--tunnel` non-interactively, defaulting to `ngrok` in agent mode) among **ngrok**, **cloudflared**, **none**, plus two interactive-only paths (`n8n`, `own server`) that just prompt for a URL to save. For ngrok/cloudflared it checks the CLI tool is installed, starts a local webhook listener on `-p/--port` (default 3000), starts the tunnel, and saves the resulting `<tunnelUrl>/webhook` as the webhook URL; (5) prints a quick-reference summary (JSON in `--json` mode). |

### Webhook Listener — `oa listen`

| Command | Description |
|---------|-------------|
| `listen [-p, --port <port>] [-s, --secret <key>] [--no-verify] [-e, --events <list>] [--path <path>] [--verify-domain <code>]` | Start a local HTTP webhook server for OA events. `-p/--port` default 3000. `-s/--secret` enables **HMAC-SHA256 MAC verification** (timing-safe compare) against the `X-Zevent-Signature`/`mac` header — a warning is printed if no secret is given. `--no-verify` explicitly disables verification even with a secret set. `-e/--events` filters to a comma-separated subset (default `all`) of: `follow`, `unfollow`, `user_send_text`, `user_send_image`, `user_send_file`, `user_send_location`, `user_send_sticker`, `user_send_gif`, `user_click_button`, `user_click_link`. `--path` changes the webhook URL path (default `/webhook`). `--verify-domain <code>` serves the Zalo domain-verification meta tag/HTML file needed at `developers.zalo.me`.
